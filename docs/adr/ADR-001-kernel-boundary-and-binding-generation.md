# ADR-001 · 内核边界与绑定生成

> 状态：已采纳（0.2.0 开工）
> 适用版本：``（参考实现/` 及以前不受本文件约束）

本文件把两条**硬规则**翻译成可执行的工程约束。
它不是建议，是这一版所有代码的准入条件。

---

## 硬规则一：业务逻辑只存在于 C 内核，UI 严禁实现业务规则

原话：

> **核心硬规则：所有业务逻辑只存在于 C 内核，UI 严禁实现业务规则。UI 只是视图层。**

### 1.1 什么叫"业务规则"（检查标准，不靠感觉）

一句话检查标准：**"这个决定，换个平台后还应该一样吗？"**

- 应该一样 → **业务规则，必须在内核**；
- 只是"这个平台怎么把它画出来" → 视图职责，允许在 UI。

把它展开成一张可核对的表：

| 属于业务规则（必须在 `native/` 内核） | 属于视图（允许在 UI） |
| --- | --- |
| 查询落到哪条词条（`resolve` / `@@@LINK` 重定向） | 把词条文字画在哪个 DOM 节点 |
| 一个查询该走哪条通道（当前词典 → 借查 → 翻译 → 终态） | 那排出路按钮摆在左上还是居中 |
| 出路有哪些（`borrow` / `recheck` / `translate`）、可不可点 | 按钮图标用哪个 SVG |
| 音节分隔点（`·‧・\u00AD`）认哪些、要不要去掉、顺序 | 提示条离输入框多远 |
| 单字符查询不做拼写纠正 | 候选列表最多画几行（**行数由内核给**） |
| 语种判定（字形 → 词典标题 → 默认语种） | 语种在提示里用什么字号 |
| 音源排序（原录音 → 系统语音 → 在线）与"这次用哪条" | 喇叭按钮呼吸动画的节奏 |
| 面向前端的一切**文案**（含"还有 N 本没能确认"） | 文案的换行、省略号、行高 |
| 缓存键、设置规范化、历史分页与上限 | 滚动条样式 |
| 词典名合成（改过的名 → 头里的书名 → 文件名） | 名字被截断时加不加 tooltip |
| 词数阈值（≤4 词说词名 / ≥5 词说"所选文本"） | —— |
| 是否清空输入、是否收起面板这类**状态机转移** | 动画时长（但转移本身由内核定） |

### 1.2 四条落地约束

1. **内核不知道界面存在。** `native/` 下任何文件都不许 `#include <windows.h>`、
   不许知道 DOM / HTML / CSS / WebView2 / JSON 之外的宿主概念。
   唯一允许的边界是**返回值**（JSON 文本 + 错误码）。
2. **UI 不许拼装面向用户的话。** 凡是用户会读到的一句话，
   它必须**整句来自内核**。UI 只负责把它放进某个元素。
   —— 现在 `main.ts` 里的 `unconfirmedNote()` / `speechPlanText()` / `按词数分两种的提示文案`
   就是这个约束的反例$1）。
3. **UI 不许持有内核也持有的常量。** 候选行数、分隔点码点、词数阈值、
   历史上限、默认音色 ID、样例词，一律**由内核导出**（见硬规则二的自动生成的文件 `constants`）。
   —— 参考实现已经为"同一个数抄在三处"付过学费（同一个数抄在三个文件里，改一处漏两处）。
4. **UI 不许做"预测式判定"。** 落点、可不可点、会不会跳 —— 一律**动手时问内核**。
   参考实现最贵的一条教训就是"选中时用字符串预测点下去的后果"
   （实例：`apples` 被 `@@@LINK` 重定向到 `apple`，预测必错）。

### 1.3 怎么强制执行（不靠自觉）

三条机械要求，缺一条视为本轮没做完：

| 要求 | 手段 | 检查标准 |
| --- | --- | --- |
| **静态检查** | `node tools/ui-boundary-check.mjs` | 扫 `web/src/**`：出现被禁符号表里的词（`@@@LINK`、`snd://`、编辑距离、分隔点码点、语种表…）→ **非零退出**；UI 里出现"看起来是给用户看的整句"（含中文标点且超过 N 字）而**没有**带 `data-from-kernel` 来源标记 → 报警 |
| **接口定义与实现一致** | `native/src/` | 每条业务规则在内核里都有断言；**UI 侧不许有同名实现** |
| **代码评审约定** | 本文件 那张表 | 新加一个判断时，先答"换平台后还一样吗" |

`ui-boundary-check.mjs` 是这一版的**新要求**，性质与参考实现的  相同
（只读源码、秒级、失败非零退出），但管的是**另一件事**：
那个管"界面上该有的东西还在不在"，这个管"界面上**不该有的东西**在不在"。

### 1.4 参考实现的现状（实测，这就是要清理的未完成项）

`web/src/floating/main.ts` 实测 **4208 行**，`manager/main.ts` **2564 行**，
`bridge.js` **622 行**。其中**住在 UI 里的业务规则**至少有这些：

| # | 位置 | 现在 UI 在做什么业务决定 | 该由内核提供什么 |
| --- | --- | --- | --- |
| 1 | `main.ts:58SEPARATOR_DOT_CODES = [0x00b7,0x2027,0x30fb,0x00ad]` | 分隔点码点表 | 内核给 `separators` 清单；判定与"要不要去掉"全在内核 |
| 2 | `main.ts:62-80isSeparatorDot` / `hasSeparatorDots` / `withoutSeparatorDots` | 分隔点的判定与剥除 | `lookup` 内部先原样问、问不到再去点问（参考实现已在内核做过一半，UI 那份是**重复实现**） |
| 3 | `main.ts:2266splitForSpeech` | 长文本切段规则（约 300 字、优先句末断） | 内核 `speech:plan` 直接给"这次切几段、每段多长" |
| 4 | `main.ts:561speechPlan` / `speechPlanText` | **音源排序**（原录音→系统→在线）与置灰原因 | 内核 `speech:status` 直接给 `chosen` + `disabledReason`（整句话） |
| 5 | `main.ts:1122unconfirmedNote` | "还有 N 本没能确认"这句提示 | `FallbackPlan.Annotate` 一处贴（参考实现的 C# 侧已有，UI 这份是**第二来源**） |
| 6 | `main.ts:1694refreshEntryChips` | 这一页**有哪些出路**、按钮可不可点 | 内核按 `chips: [{action,label,enabled}]` 给 |
| 7 | `main.tscountSelectedWords` + ≤4/≥5 阈值 | 词数阈值与按词数分的两种文案 | 内核给整句（已选几个词是内核的判断） |
| 8 | `main.ts:40MAX_LIST_ROWS = 8` | 候选行数 | 内核导出常量 |
| 9 | `main.ts:4027` / `explainAudioFailure` | 音频失败原因翻译成人话 | 内核给 `reason` 整句 |
| 10 | `manager/main.ts:637DOUBAO_DEFAULT_VOICE_*` / `SAMPLE_WORDS` | 默认音色 ID、试听样例词 | 内核导出常量 |

**这 10 条就是 0.2.0 第一阶段要清掉的东西。** 清理的验收检查标准不是"我觉得清完了"，
而是 `ui-boundary-check.mjs` 全绿 + `main.ts` 行数下降（记录在案）。

## 硬规则二：唯一的接口定义文件，绑定自动生成

原话：

> **通过统一头文件自动生成各平台绑定、内核自带完整单元测试、操作系统相关的那一层做薄，避免重复工作。**

### 2.1 唯一的接口定义文件

`
abi/lookup.abi.json      ← 唯一的接口定义（人写，只有这一份）
`

从它**生成**出去的东西（全部是产物，**禁止手改**，头部带 `GENERATED — DO NOT EDIT`）：

| 产物 | 消费者 | 为什么必须生成 |
| --- | --- | --- |
| `native/include/dsh_lookup.h` | C 内核实现、C 测试 | 声明与规格不可能漂移 |
| `shell/Lookup.Interop/LookupInterop.g.cs` | **Windows 现有 C# 壳**（0.2.0 的宿主仍用 C# + WebView2） | 壳能带着参考实现的全部验证继续用，不必先重写宿主 |
| `web/src/shared/abi.ts` | TypeScript UI（`api.*` 的类型与常量） | UI 侧的类型与常量与内核同步 |
| 测试 | 测试诊断 / 冒烟 | 诊断用的符号名与位数不错位 |
| `docs/api/abi.md` | 人读 | 接口定义文档自动与实现同步 |

> **为什么不去手写一份 `lookup.h` 再手写一份 P/Invoke**：那正是参考实现反复吃亏的形态。
>  / `smoke-test.mjs` / 页面三方各抄一份 `MAX_LIST_ROWS`，
> 抄错一次症状是"诊断按另一个条数问主进程 → 对账全红 → 看着像应用坏了"
> （同一个数抄在三处），最后只能立一条 标准人工盯着。
> **改成生成，这类检查标准就不需要了 —— 因为它们不可能不一致。**

### 2.1b 自动生成的文件**不能被自动生成的文件校验** —— 必须另立一份人工对照物

接口定义是唯一来源，于是有个陷阱：**接口定义改了、生成脚本跟着改，产物永远自洽**，
而接口定义本身可能是错的。所以另立两份独立的防回归检查：

| 手段 | 位置 | 管什么 | 为什么它咬得住 |
| --- | --- | --- | --- |
| 接口定义编译自检 | 测试 | ① 生成的头文件能过 `-std=c11 -Wall -Wextra -Werror -pedantic`；② **34 条声明逐条被调用一次**（放在 `if (0)` 里，永不执行），返回值赋给 `enum dsh_error` 变量并由 `_Static_assert` 核对；③ 常量 8 个与分隔点 4 个码点逐条对 | 假参数与断言是**人**写的。生成脚本改坏了、或接口定义与这份对照脱节，要么编不过、要么断言红 |
| 接口定义完整性检查 | `node tools/gen-bindings.mjs --check` | 产物与接口定义**逐字节**一致（有人手改产物就红；`--check` 只读不写，可进 CI） | 机械检查标准，不依赖任何人记得 |

⚠️ **`if (0)` 与 `-Werror` 的组合是这条检查标准的命门**：里面的变量只在永不执行的分支里用过，
所以"把 `if (0)` 改成 `if (1)`"或"删掉某条调用"都会**编不出来**。
少了这层，检查标准就会误报通过（参考实现那个坑的同族：检查标准钉错了对象，或钉的东西不会失败）。

**同一天被它暴露出来的四件事**：
1. `void` 在"返回值"与"参数"两个位置含义不同，一个类型映射表达不了 → 另立 `opaque` 类型；
2. 句柄的前置声明 `typedef struct dsh_engine dsh_engine;` 漏生成（`spec.types` 有一处没换成 `typeMap`）；
3. 星号合并规则写错：出参成了 `char * *out`、标量成了 `size_toffset`；
4. 我给自检加的**第一条**检查标准就判反了（"返回值星号后面不许有空格"），把合法的
   `const char * dsh_version(void);` 判成错误 —— **检查标准写错比没有检查标准更坏**，
   它会让人去"修"一个没坏的东西。

### 2.2 接口定义定什么东西（四类）

| 类 | 内容 | 生成到各语言的什么 |
| --- | --- | --- |
| `types` | `Handle` / `i32` / `usize` / `utf8` / `json` | C 类型；C# `IntPtr`/`int`/`string`；TS `number`/`string` |
| `enums` | `ErrorCode` / `Outcome` … | C `enum`；C# `enum`；TS 常量对象 |
| `functions` | 名字、参数、返回、`release` 规则 | C 声明；C# `[DllImport]` + 释放包装；TS `api.*` 签名 |
| `constants` | 候选行数、词数阈值、分隔点、默认音色、历史上限… | C `#define`；C# `const`；TS `export const` |

### 2.3 内存与字符串的硬约定（跨语言唯一容易出事的地方）

1. **内核返回的每一块内存都由内核分配、内核释放**，一律用
   `dsh_release(void *)` 还给内核。宿主**禁止** `free()` / `Marshal.FreeHGlobal` 它。
2. **字符串一律 UTF-8 且以 `\0` 结尾**；带二进制的（音频）另有 `(ptr,len)` 接口。
3. **返回结构体一律"输出参数 + 错误码"**：
   `dsh_error dsh_lookup(...)`，成功时把 JSON 文本写进 `const char **out_json`。
   不用"返回指针 + 查询错误"那种两段式（宿主容易忘查）。
4. **JSON 是唯一的数据交换格式**（参考实现已经在用，且已有 `Newtonsoft` / 原生 JSON 两条路），
   但**故意不把 JSON 当"随便什么都能塞"的袋子**：每个接口的 JSON 形状由
   `abi/lookup.abi.json` 里的 `resultSchema` 字段写清，并由 生成脚本产出文档。
5. **句柄不透明**：`dsh_dict *` 在宿主侧只是 `IntPtr`，宿主不许解释它的位。

### 2.4 错误编码

`c
typedef enum {
  DSH_OK = 0,
  DSH_E_INVALID_ARG,   /* 参数不合法（空指针 / 空词） */
  DSH_E_NOT_FOUND,     /* 文件不存在或不是 MDict —— 必须与"没有这个词条"分开 */
  DSH_E_FORMAT,        /* 能打开但不是合法 MDict */
  DSH_E_IO,
  DSH_E_OOM,
  DSH_E_STATE,         /* 句柄状态不对（未 open 就 lookup） */
  DSH_E_NOT_IMPLEMENTED
} dsh_error;
`

**`DSH_E_NOT_FOUND` 与"查不到这个词条"必须分开** —— 这正是参考实现那个坑的形态
（拿一个不存在的路径去建记录会安静地成功，因为 `FileInfo` 不抛异常）。
内核这一层把它变成**类型上不可能混淆的两件事**。

### 2.5 操作系统相关的那一层做薄的约定

平台层（`platform/windows/`、将来 `platform/linux/`…）**只允许做四件事**：

1. 开窗 / 收窗 / 托盘 / 焦点 / 吸边（宿主 OS 的窗口 API）；
2. 承载 WebView，把内核给的资源（HTML / dist JS / `.mdd` 里的资源字节）喂给它；
3. 把界面发来的 JSON-RPC 请求**原样**转给内核，把内核的 JSON 原样转回去；
4. 系统能力：剪贴板、系统 TTS、HTTP、随机数、时钟、配置目录。

**禁止**在平台层出现任何 `if (词长得像…)`、任何语种判断、任何"要不要去点"的判断。
检查标准：**平台层里不许出现面向用户的中文文案**（除调试日志）。

## 附：这份 ADR 与仓库既有规范的关系

- 本 ADR **不豁免**仓库规范里的任何硬规则（尤其测试分级与完整测试次数）。
- 0.2.0 的测试分级沿用同一张表，只是**手段换成内核自带的 C 测试**：
  内核单元测试 = A/；`kernel-e2e` 诊断 =；完整测试冒烟仍是。
- 参考实现继续作为**参考实现**存在（不是"冻结归档"，而是"逐字节对照基准"），
  直到 0.2.0 的标准答案文件逐字节对照全绿为止。
