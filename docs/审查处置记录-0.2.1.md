## 一 安全发现

### F1 · P1：不可信词典脚本能够触发翻译动作

**报告说的**：词条正文住在 `sandbox="allow-scripts"` 的跨源 iframe 里，消息处理只检查
`data.source === 'lookup-entry'`（发送方自己填的字符串，没有认证作用）。词典自带的脚本与桥接脚本
**跑在同一个 JS 环境**里，所以它可以直接 `parent.postMessage` 一条 `chip: translate`，让宿主把
**它指定的文本**发给收费的翻译接口。报告明确写了「**只加 source 校验不能解决**当前词典自身的恶意脚本」。

**处置：把授权还给可信父页面。**

- 出路按钮（「再问一遍」/「翻译这个词」）**改由宿主页自己渲染** —— 容器是
  [`web/floating.html`](../web/floating.html) 的 `#entryChips`，渲染器是
  [`web/src/floating/main.ts`](../web/src/floating/main.ts) 的 `renderEntryChips`。
  位置从「词条正文末尾」挪到「正文框顶部、紧跟那行解释」。
- 前端消息处理器**删掉了 `type === 'chip'` 那一支**：正文那边**一个动作都换不出来**了。
- 顺带补上报告要求的另外两层：**来源校验**（`event.source === entryFrame.contentWindow`，
  挡别的窗口冒充正文框）与**结构校验**（类型/有限性检查后才使用）。
- 代码里两处注释写清了这条边界的**适用范围**：来源校验挡不住同一环境里的词典脚本，
  也**不许**用「给正文发令牌再收回来」或 `Event.isTrusted` 代替真实点击的授权。

**证明**（[`tools/check-entry-auth.mjs`](../tools/check-entry-auth.mjs)，A′ 级：不启动程序、秒级）：

- 从**真实的** `main.ts` 切出消息处理器与 `renderEntryChips`，去类型后在 vm 里拿桩跑 ——
  **不是**照抄一份逻辑来测（抄的那份只会证明"抄对了"）。
- 决定性的一条：`event.source` 设成**真正的正文框窗口**（词典脚本所在的那个环境）再发
  `chip: translate` → **到不了任何动作**。
- 反向对照：正文框发来的合法 `entry://` lookup、`dead-click` 照旧送达；别的窗口发来的一律丢弃；
  外壳页面的桥调用照旧正常。
- **这条检查拿"修之前的那份代码"跑过，是红的**（`DSH_ENTRY_AUTH_TARGET` 指向 0.2.0 那一份
  `main.ts`，4 项失败、退出码 1）—— 一条旧代码也全绿的检查等于什么都没守。

### F2 · P1：记录块累计长度可发生有符号整数溢出

**报告说的**：`native/src/dict/dsh_mdx.c` 里 `pack_acc += rb[i].pack_size` /
`unpack_acc += rb[i].unpack_size` 没有溢出检查；单个 8 字节整数合法（`read_be` 允许到 2^53）
**不代表总和合法**。一个 16,720 字节的合成文件（1,025 项各声明 2^53）让 `dsh_mdx_open` 触发 UBSan。
报告也点了 `read_key_infos` 需要同样检查，并要求**压缩范围落在文件内、索引项数与索引字节长度匹配**，
且「不能只靠校验和警告兜底」。

**处置**：在 `dsh_mdx.c` 里立起一套**先算上限、再分配；先比大小、再相加**的规矩
（文件顶部有一段说明写清了为什么这个文件需要它），并把索引项数/字节数纳入统一的预算检查。

### F3 · P2：很小的异常文件可诱导超大索引分配

**报告说的**：解析器允许最多 10,000,000 个词块，并且在「验证信息块装得下多少索引」**之前**
就按声明数分配并清零。346 字节的合成文件诱导申请 **640,000,000 字节**。报告要求
「先按信息块实际长度推导最大可能条数，再分配」，并点名 `dsh_mdx_list_keys` 要纳入同一次检查。

**处置**：新增 `index_budget_ok()`（条数非负、不超条数上限、字节数不超预算）等统一的分配前检查，
**先查再分配** —— 因为 `count * sizeof(T)` 自己会溢出，而 `count` 是文件说了算的。

**F2/F3 的证明**：

- **B 级**（`wsl.exe -- bash tools/wsl-make-test.sh`）：逐组 **28 行**（基线 27 组 + 新增的
  `mdx_hardening`），**全部「失败 0」**；`mdx` 仍是 155 项、其余各组项数与基线逐一相同
  （**没有一组消失、没有一组变数**）。
- **内存检查**（`make asan`，ASan + UBSan）：**exit 0**，同样 28 组全 0 失败，
  且 `runtime error | AddressSanitizer | LeakSanitizer | SUMMARY | ERROR:` **一条都没有**。
- **报告里那两个畸形文件，修前 vs 修后（用 `logs/audit-2026-09-29/` 的原始复现件，只读）**：

  | 复现件 | 修之前 | 修之后 |
  | --- | --- | --- |
  | F2 `overflow.mdx`（16,720 字节） | UBSan 报 `signed integer overflow: 9214364837600034816 + 9007199254740992`（`-fno-sanitize-recover` 下退出 1） | `open_rc = -1`，人话错误：「声明的解压后大小 9007199254740992 超出单块上限 536870912 字节」，**无任何 sanitizer 输出** |
  | F3 `huge-count.mdx`（346 字节） | 单次最大分配 **640,000,000** 字节 / 合计 640,009,825 | 单次最大 **8,192** 字节 / 合计 **9,843**；词块索引数组的分配量 **0**（在分配之前就按信息块 32 字节推出「最多 1 条」并报错） |

- **不许改坏别的**：23 份冻结素材（`testdata/*.mdx|mdd` + `variants/*.mdx`）逐份新旧对比，
  打开结果 / 键数 / 块数 / 解压总量 / 警告数**逐字相同**；`big.mdx` 的 20 万键照常全部枚举。
  C 级那道门（见下）也把这一条钉死了：**21/21 与冻结基线逐字节相同**。
- 口径说明（免得下一个人以为"上限拦住了就是修好了"）：报告里那个 F2 文件现在是先被
  **单块 512 MiB 上限**拦下的（2^53 > 512 MiB）；**累加溢出检查是第二道防线**，
  由新增用例「64 块 × 1 MiB 超总量预算」单独覆盖。这是有意选择 —— 512 MiB 正是
  `dsh_inflate` 自己就会拒绝的口径。

## 二 工程缺陷

### F4 · P2：公开仓库不能按现有说明完整构建 DLL

**报告说的**：`tools/build-windows-dll.sh` 只认项目内 `.toolchain/mingw/sysroot`，**不使用 `PATH`
里已装的 MinGW**；报错让人去跑 `tools/build-mingw-sysroot.sh` —— **而那个脚本根本不存在**，
于是「编不出来」变成「照提示做还是编不出来」。

**处置**：

- 交叉编译器按**三级**查找：① `DSH_MINGW_ROOT`（可指 sysroot / MinGW 前缀 / gcc 本体）
  → ② `PATH` 里的 `x86_64-w64-mingw32-gcc` → ③ 项目内 `.toolchain/mingw/sysroot`。
- 新增 `--preflight`：报出**用的是哪一套、什么版本、sysroot 在哪**，并试编一个最小 DLL ——
  「这次到底用了哪个编译器」从此可问、可答。
- 找不到时的报错**逐条列出找过哪些地方**，并指向真实的安装说明；删掉对不存在脚本的引用。
- 安装说明（版本、`apt-get download` + `dpkg-deb -x` 的可复现步骤、预检命令）写进
  [`native/README.md`](../native/README.md)；**仓库里存的是版本与装法，不是工具链二进制**
  （`.toolchain/` 仍在 `.gitignore` 里）。

**证明**：

- **修之前**（把未改动的脚本拷到 `/tmp`，仓库根给本仓库）：**退出码 2**，唯一输出
  `找不到交叉 gcc，先跑 tools/build-mingw-sysroot.sh` —— 照它做也没有那个脚本。
- **修之后**：`sh tools/build-windows-dll.sh Release` → **exit 0**；
  `接口定义 49 条，已实现 49 条 → 导出列表` / `dsh_lookup.dll（872,134 字节）` /
  `dsh_lookup.def（52 行）` / `接口定义 49 条；DLL 导出 49 条；未实现 0 条` /
  `✅ 导出表只含接口定义里的接口（无内部符号泄漏）；已实现的 49 条全在`。
  `objdump -f` → `pei-x86-64`；`objdump -p` 的 `DLL Name` **只有 KERNEL32.dll 与 msvcrt.dll**。
  Debug 那一支也验过（1,526,934 字节，49/49）。
- **`--preflight`**（新增，F4 要的"能不能先确认工具链可用"）：报出**来源 / 编译器路径 /
  `--version` / `-dumpmachine` / 头文件目录 / 库目录 / sysroot**，查 `python3 nm objdump find sed tr`
  是否都在，然后**真编一个最小 DLL** 并用 `objdump -f` 验格式。
- **干净失败**：`DSH_MINGW_ROOT=/tmp/definitely-not-a-toolchain sh tools/wsl-build-win.sh` →
  **退出码 2**，并逐条列出"探过哪两处 + 这个变量可以指什么 + 装法在哪一篇文档"。
  （显式指定的路径**不回落**：指错就当场失败，绝不静默换一个编译器。）
- **工具链装法是从零跑通的**（不是照抄）：`apt-get download` 那 5 个 `.deb` → `dpkg-deb -x`
  解成 330 MB 的 sysroot → 用它真编出 DLL。包与版本号见 `native/README.md`
  （`gcc-mingw-w64-x86-64-win32 13.2.0-6ubuntu1+26.1` 等，实测记录）。
- ⚠️ **一条给发布记录的实测**：同一份源码连编两次，**体积稳定（872,134 字节）但字节哈希不稳定**
  （差 4 个字节，其中 `0x88` 那处经 PE 头确认是 COFF `TimeDateStamp`）。
  所以版本记录请钉**体积 + 导出表**，**别钉哈希**；要钉哈希得加 `-Wl,--no-insert-timestamp`。

### F5 · P2：生成绑定与接口定义检查失败

**报告说的**：`node tools/gen-bindings.mjs --check` 退出 1；差异在 `dsh_lookup.h:437`（注释残留 `$1`）、
`:591` 与 `abi.ts:102`（措辞）—— **全是注释，没有签名/枚举/常量漂移**。报告要求从接口定义重新生成，
并指出「生成注释需修改规格/生成器，不再手改产物」。

**处置：确认**不是**生成器的 bug，修复层是产物（重新生成）。**

根因查清了（这一步值钱，所以记下来）：这三处是**一次脱离生成流程的全树注释清扫**留下的 ——
原工作区里那个脚本按规则表改注释区间，其中一条规则的**模式里一个捕获组都没有**、替换串却写了 `$1`，
而 JS 的 `String.replace` 在"模式无第 1 组"时把 `$1` **当字面量**写出去；它只在 C 头文件里命中，
因为那份注释是**折过行**的，「见」正好落在行尾。旁证：生成器自那以后**哈希未变**，
而产物里出现了生成器从未产出过的措辞。**所以生成器、规格都没改，重新生成即可。**

- `node tools/gen-bindings.mjs` → 四份写出；`--check` → **退出码 0**。
- 「只动注释」用仓库自己的 `tools/comment-diff.mjs` 证明了（`✓ 只动了注释 … 代码逐字符相同`），
  签名 / 枚举 / 常量一个字符没动；BOM 与换行不变。

**顺带的加固（针对"为什么能潜伏下来"）**：

- `--check` 失败时**打印行级差异**（先吃公共前缀/后缀，只报中间那段），并直接给出修法。
  原先只报"旧 N 字符 / 新 M 字符"，看不出差在哪 —— 那会把人推向"手改产物去凑绿"，
  正是这次事故的形态。
- CI 接上这道检查（见 §四）。

## 三 加固项与文档漂移

报告「加固项与文档漂移」那一节的三条，逐条处置：

1. **`WebViewBridge.cs` 的 `OnWebMessage` 没有验证消息来源 URI** →
   已在进 `Dispatch.Handle` **之前**加来源校验：只有外壳自己的页面（`https://lookup.local`，
   即 `VirtualHost.ShellDomain`）能调桥；不是的话**丢掉并记账**（`RejectedMessages` /
   `RejectedMessageSources` / `MessagesSeen`）。

### 6.3 ★ CI 第一次真跑，照出一个**本地永远照不出来**的 bug

把 0.2.1 推上 GitHub 之后，`.github/workflows/ci.yml` 第一次真跑：**6 个 job 里 5 个绿**
（内核单测 + ASan/UBSan、静态检查、交叉编 DLL、格式矩阵对照测试 —— 在**干净的 runner** 上
从零跑通，这本身就是"恢复的维护能力是真的"的一个旁证），**只有 Windows 侧那个 D 级 job 红了**：

```
tools/test-windows-dll.ps1:45  Unexpected token 'å†…æ' in expression or statement.
tools/test-windows-dll.ps1:45  Missing closing ')' in expression.
tools/test-windows-dll.ps1:53  Unexpected token ':' in expression or statement.
tools/test-windows-dll.ps1:81  The string is missing the terminator: '.
```

根因（本地复现靠"把文件按 cp1252 解一遍再解析"，因为**本机复现不了这个现象**）：

- **Windows PowerShell 5.1 读没有 BOM 的 UTF-8 文件时，按机器的 ANSI 代码页解码。**
- 本机 ANSI 代码页**正好是 UTF-8**（`chcp` = 65001）→ 本地怎么跑都对 → 这个 bug 一直潜伏着。
- runner 上是 **1252**：中文注释被解成乱码，而乱码里会出现 `’`（cp1252 的 `0x92`）这类
  **被 PowerShell 当成单引号**的字符 → 字符串没闭合 → **整个脚本语法错误**。
- 实测范围：**13 个 `tools/*.ps1` 在 cp1252 下各有 3–24 处语法错误** ——
  也就是说**整套 Windows 侧工具链**（`package.ps1` / `test-shell-app.ps1` /
  `test-windows-dll.ps1` / `probe-*.ps1` …）在**ANSI 代码页不是 UTF-8 的机器上根本跑不了**。

⚠️ 这与本项目**早就知道的那一类**是同一个病根：`native/Makefile` 的两条静态检查
（"业务层不许自己开文件""平台层不许用 A 版 Win32 路径 API"）防的就是"**本机代码页是 UTF-8、
本地照不出来**"。那两条盯的是**运行期**的窄字符 API；这一条盯的是**脚本文件自己的编码** ——
同一个教训换了个地方出现。

修法：**给 `.ps1` 加 UTF-8 BOM**（PowerShell 见到 BOM 就按 UTF-8 读，与机器代码页无关）；
`.sh` / `.json` 反过来**不许**带 BOM（前者会把 BOM 顶到 shebang 前面，后者会让 `JSON.parse` 报错）。
13 个文件的**正文一个字节没改**（逐文件哈希比对过），只是前面多了 3 个字节。

并且加了一条机械保证：`tools/check-encoding.mjs`（秒级、不启动程序）钉住
"`.ps1` 必须带 BOM / `.sh` 与 `.json` 不许带 / 其余文本必须是合法 UTF-8"，
CI 里也跑；规则写进 `AGENTS.md` §二 第 15 条。

> 附带一条经验：这条检查自己第一次跑就**报了个假阳性**（说 `tools/golden/baseline/golden-baseline.json`
> 不是合法 UTF-8）—— 而那份基线**本来就带着 GBK/BIG5 词典的原始字节**
> （`tools/golden/compare-golden.py` 的 `load()` 是按 `errors='replace'` 解的）。
> 于是给它加了一条**有说明的豁免**，而不是把整条"必须是合法 UTF-8"的检查放宽掉。

  F2/F3 动了 `dsh_mdx.c` 之后，正是它证明"23 份样本的解析行为**逐字未变**"。
  它现在是**变更探测器**，不再是"与另一个实现对齐"的证据。
- **参考实现的源码移出仓库**：它只剩一个用途 —— 重新生成那四样东西
  （`entry_assets.h`、`entry_doc_vectors.h`、`html_vectors.h`、冻结基线）。
  日常回归、构建、打包都不需要它。

**怎么做的**（顺序有讲究，因为"移走之后那三份产物就再也改不动了"）：

1. **趁参考实现还在**，先改两个生成器（`tools/golden/entry-assets.cs`、`html-vectors.cs`）里那几句
   "来源：reference/…"的注释 —— 改成**不带路径**的说法（"那份参考实现不随本仓库发布；
   要取回来见某个**脚本**的提示"），再**重新生成**三份产物。于是签入的产物既不会永久指向一个
   不存在的路径，也不会指向一份**已经不存在的说明**。
   重生成后 `make test` 复跑：`entry_doc` 102、`html` 243，**28 组全 0 失败**（只动注释）。
2. 打包归档、**逐文件 SHA256 校验**（18 个文件、0 处不符），包
   `reference-0.1.3-parser.zip`（73.4 KB，SHA256 `71eb1e2e…`），与原 0.1.x 的归档放在一起。
   —— 取回来与重生成的完整步骤记在**归档目录**那一侧（`archive/README.md`），
   仓库里只留"缺件时怎么办"的提示。
3. **`reference/` 整个目录删掉**（不留在仓库里当路标）。用户看过第一版留下的
   `reference/README.md` 之后指出：**从浏览者的视角看，一篇解释"这个目录为什么是空的"的说明
   云里雾里，不如没有这回事。** 采纳 —— 于是仓库里**既没有参考实现，也没有关于它的目录**。
4. **让四个重生成入口"缺件时给人话"**：`make-entry-assets.ps1` / `make-html-vectors.ps1` /
   `make-golden.ps1` / `run-golden.sh --regen` 现在都会**打印归档包名 + SHA256 + 取回来的三条命令**
   再停下（退出码 1 / 3）；`freeze-fixtures.ps1` 则**明着说一句"参考实现不随本仓库发布、跳过它的
   校验"**而不是静默少核一份东西。三个 `.csproj` 里也加了同样的提示（免得有人直接 `dotnet build`
   拿到一串看不懂的 C# 错误 —— 那正是 F4 当初那种"照提示做还是不行"的死胡同）。
5. 把文档里**所有**"参考实现在 `reference/…`"的说法逐处改口成
   **"参考实现（上一代 C# 实现）**不随本仓库发布**"** —— 一条路径都不留：
   `README.md`（正文两处 + 目录表那一行）、`AGENTS.md`（§二 第 12 条、§七 第 2 条）、
   `native/README.md` 术语表、`docs/design/` 四处、冻结基线的 `provenance.md` / `README.md`。

**做完之后的复验**：C 级对照测试**仍然 21/21 通过**（仓库里根本没有那棵参考树），
冻结件校验明着跳过参考实现那份后照常退出 0，A / A′ / B 三道门全绿，
全仓**提不到** `reference/0.1.3-parser` 这个路径。
