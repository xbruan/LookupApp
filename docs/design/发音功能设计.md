# 词典发音功能 · 设计文档

> **这份文档的用途**：把发音这件事说全 —— 三层音源各管什么、字节从哪来、谁来出声、

## 0. 一句话结论

发音功能的三层音源**全部已经接上**：词典自带的原录音（多卷 `.mdd` 里的 `.spx` 也解得开）、
在线（豆包单向流式 HTTP）、系统离线（Windows 的 SAPI5，经 .NET 的 `System.Speech`）。
输出侧是宿主页里**一个全局复用的 `<audio>`**，增益走 Web Audio 的 `GainNode`。

当年那份设计里「真正缺的三件事」是这样收口的：**宿主接住播放**（已做，连例句音频一起）、
**`snd://` 与 JS 驱动播放**（已做）、**Speex 解码**（已做 —— 不再是"不做"，而是**vendor 了官方
libspeex 的解码路径编进内核**，见第 3.1 与第 15 节）。

今天**唯一**还明确没做的是「查词后自动发音」（用户当初就拍了不做，代码里也一个字都没有）。

## 1. 实测事实（决定方案的地基，不要重复验证）

用只读的诊断脚本扫过用户自己那 4 本词典（那时用的工具属于参考实现那一代，**本仓库里没有对应物**）：

| 词典 | 发音链接长什么样 | 音频在哪 | 结论 |
| --- | --- | --- | --- |
| **LDOCE5** | `<a href="sound://GB_brelasdeapple.spx"><img src="snd_uk.png"></a>`、`sound://US_apple1.spx`；例句 `sound://p008__000944636.spx` | `LDOCE5.1.mdd`（**185,713 个键**，键名带前导 `\`，如 `\GB_brelasdeapple.spx`） | 英音+美音都有，**最理想的一本** |
| **牛津高阶 9** | `snd://apple__gb_1.spx` / `snd://apple__us_1.spx`（**另一种 scheme**），配 `<audio-gb>🔊</audio-gb>`、`<audio eid="apple_audio_1" name="apple__gb_1">` | 用户的 `.mdd` 只有 **1,388 个键**，`locate \apple__gb_1.spx` 未命中 | **音频不在这个 mdd 里**（大概率缺 `.1.mdd`）→ 只能走兜底音源 |
| **AHD4 双解** | 正文里 `sound://` 出现 **0 次** | 有 `.mdd`（45 MB）但无音频 | 无音频 |
| **韦氏大学 11** | — | 没配 mdd | 无音频 |

**关键实测（最大的技术障碍）**：把 spx 从 mdd 里抠出来看头部 —— 1667 字节、`OggS` 容器、
**Speex 1.2rc1**。是 Ogg Speex，**不是 Vorbis 也不是 Opus**。Chromium（WebView2）**不解码 Speex**，
所以"把 `sound://` 变成一个能播的 URL"这条路走不通 —— 只能自己解（今天由内核解，见第 15 节）。

**本机离线语音**：SAPI5 只有 `Microsoft Zira (en-US)`；OneCore 里只有 3 个中文音色、**英文 0 个**。
→ 离线兜底目前只能出**美音**；要英音得让用户在 Windows 里装语音包。
（这条后来促成了一次"接了 OneCore 又撤回"的往返，结论与理由见第 16 节。）

**这些数字的来源**：一次只读扫描的结论。**本仓库里没有那次用的那些诊断脚本** ——
它们属于参考实现那一代，**一个都没有搬进来**。落地前如需精确覆盖率，今天可用的只读入口是：

- 内核单测 `native/tests/test_audio.c`（素材是冻结在仓库里的 `testdata/audio.mdx` + `audio.mdd`）；
- C 级定向观察 `node tools/probe-page.mjs --dict-samples`（拿用户自己的真词典，要程序跑起来）；
- 以及 `native/tests/test_dictsample.c`（取样策略本身，不启动程序）。

## 3. 整体设计：三层，各管一件事

```
① 触发层  谁说要发音？  词典自带喇叭（词条里的响声） / 标题栏统一发音按钮 / 正文选中文字的「朗读」
② 供给层  字节从哪来？  词典自带原录音（多卷 .mdd；.spx 由内核解成 WAV）
                        → 在线（豆包 · 单向流式 HTTP，SSE）
                        → 系统离线（SAPI5 合成 16bit PCM WAV）
③ 播放层  谁来出声？    宿主页里一个全局复用的 <audio>；增益走 Web Audio 的 GainNode
```

**顺序是产品约定，用户不给选。** `native/src/audio/dsh_speechplan.h` 顶上那段约定写得很直白：
顺序是**词典自带 → 在线 → 系统离线**，「用户不给选（多一个开关只会让用户以为『我选了在线却没走在线』）。
所以界面只许照抄内核算出来的结论」。

**这一层与「平台能力」的分界**（同一份头文件）：

- **壳负责探测**：本机装了哪些离线音色（Windows 上要问 `System.Speech`），把那张表原样交给内核；
- **内核负责判断**：走哪一层、哪个语种配哪个嗓子、能不能点、不能点时那句人话。

依据：`native/src/audio/dsh_speechplan.h`、`native/src/engine/dsh_speech_api.c` 的 `dsh_speech_plan`、
`abi/lookup.abi.json` 里 `dsh_speech_plan` 那条注释。

> **与原文的差异**：原文的优先级是「本词典自带音频（英/美）→ **系统语音（离线）** → 在线 TTS（可选，默认关）」。
> **现在是「词典自带 → 在线 → 系统离线」** —— 在线**排在系统离线之前**，而且**没有"默认关"这个开关**。
> 依据：`native/src/audio/dsh_speechplan.h` 顶上那四条约定、
> `native/src/audio/dsh_speechplan.c` 的 `dsh_speech_plan` 那三层的数组顺序。

**为什么播放层选 WebView2 里的 `<audio>` 而不是原生播放**：Chromium 自带
mp3/aac/wav/ogg-vorbis/opus/flac 解码器（**除 Speex 外**一种都不用自己写），`<audio>` 还能天然接住
词典自己 JS 驱动的播放；壳那边只要把字节喂过去。反过来走原生播放，mp3 得引
MediaPlayer/NAudio、ogg/opus 还得自己解，反而更重。
**额外收益**：WebView2 / WKWebView / WebKitGTK 全都自带这些解码器，这条选择同时买下了将来的可移植性。

### 3.1 Speex：这功能里唯一一块"真算法"

当初的五个选项（那一代的产品是纯托管 C#，所以都在「怎么在托管侧解 Speex」里挑）：

| 方案 | 代价 | 评价 |
| --- | --- | --- |
| **纯 C# 解码器**（vendored NSpeex，BSD） | 源码约 10 个文件，编译进 exe **+60~150 KB** | 那一代的**推荐**：无原生库、无联网，可在服务端解完缓存成 WAV |
| WASM 版 Speex（塞进 exe 或 `web/dist`） | +100~250 KB，且要改前端构建链 | 备选，测试比 C# 麻烦 |
| 原生 `libspeex.dll` P/Invoke | 多一个原生 DLL | 那一代**不推荐**：违背"缩体积"的初衷 |
| 依赖 ffmpeg / 外部转码 | 用户要另装工具 | 不做 |
| **不解析 Speex** | 0 KB | LDOCE5 自带音频**永远放不出**，等于核心功能没做 |

**内核是纯 C11，「多一个原生 DLL」这条理由不存在了** —— 于是选型直接落到**官方 libspeex 的源码**：

- `native/vendor/speex/`：官方 **libspeex 1.2.1** 的**解码路径**。许可 **BSD 3-Clause**
  （`COPYING` 原样留着，含"不得用 Xiph.org 的名义为衍生品背书"那一条）。放了
  `include/speex/` 6 个公共头 + `libspeex/` 上游 `libspeex_la_SOURCES` 里那**全部 30 个 `.c`**；
  没放编码器专用件与 FFT（前处理/回声消除才要的）。
- **我们自己写的只有三个文件**：`speex/libspeex/config.h`（autotools `config.h` 的手写等价物，
  里面定下浮点/定点那个开关）、`speex/include/speex/speex_config_types.h`（同上）、
  `speex/dsh_override.h`（把上游 `_speex_fatal` 里的 `exit(1)` 换成"打印一句、返回"——
  内核的硬规则是"绝不让任何东西把进程掀翻"）。
- **容器与打包不在 vendor 目录**：Ogg 页重组 / Speex 头字段 / 逐帧循环 / WAV 封装在
  `native/src/audio/dsh_speex.c`，是从参考实现的 `OggSpeex.cs` 逐条移植过来的
  （连错误文案都逐句照抄 —— 那些话是直接显示给用户的）。

实现要点：容器解析 → 读 Speex 头（采样率 / mode / 声道 / `frame_size`）→ 逐帧解 PCM →
包成 16bit PCM WAV（44 字节头 + PCM）。感知增强（`SPEEX_SET_ENH`）**开着**，与 libspeex 系播放器的默认一致。
PCM 出参有 **64 MB 上限**（16 kHz 单声道约 35 分钟），防一段畸形码流把内存吃光。

⚠️ **一个骗过两个人的坑**：**播放速率要取头里写的 `rate`**，不要用「模式速率」（8000/16000/32000）。
LDOCE5 那种 `rate=22050 / mode=1 / frame_size=320` 的文件已经骗过两个人，两次都是用户听出「声音偏低」
才纠回来的。这条写在 `native/src/audio/dsh_speex.h` 的 `dsh_speex_info.rate` 那一项上。

### 3.2 供给层：音频路由

三条路由，都落在同一个 Range 感知的出口上：

- `/__sound__/<词典 id>/<键名>`（**外壳站点** `lookup.invalid`）—— 宿主页在播时走这条；
- `https://<词典 id>.dictres.invalid/__sound__/<键名>`（**词典资源域**）—— 词条正文自己播时走这条
  （词条 iframe 是跨源的，取不到外壳站点那条）；
- `/__speech__/<缓存键>`（**外壳站点**）—— 系统离线与在线**合成**出来的字节走这条。

Range 语义：`Accept-Ranges: bytes`、带 Range 回 **206 + Content-Range**、越界回
**416 + `bytes */total`**。（原文说"短音频不给 Range 也能播"；实际按规范补齐了，因为 `<audio>`
会先发 `Range: bytes=0-`，而且它是 seek 的前提。依据：`shell/Lookup.Host/VirtualHost.cs`。）

**格式判定是"先看魔数、再看扩展名"**，顺序不能反 —— mdd 键名是词典作者写的，写错扩展名是常事：

- 能直接播的格式（mp3 / wav / ogg-vorbis / opus / mp4 / flac）**原样发出** + 嗅探出来的 MIME；
- `.spx`（Ogg Speex）**就地解成 WAV** 再发，`mime` 报 `audio/wav`、`decoded = true`；
- 解不开就**如实报错**（`audio/x-speex` + `playable = false` + 一句人话），
  **不许让播放器去报一个用户看不懂的错误码**，也**不许拿 TTS 假装顶上**。

依据：`native/src/engine/dsh_speech_api.c` 的 `dsh_audio_prepare`（`detect_codec` / `sniff_mime` /
`dsh_speex_looks_like`），接口定义 `abi/lookup.abi.json`。

### 3.3 触发层：三条路都要接上

1. **词典自带喇叭**（LDOCE5 的情形）：`<a href="sound://…">` 已被桥接脚本捕获 → 宿主接住
   `play-sound` → 送进那个全局唯一的 `<audio>`。LDOCE5 的喇叭图标（`snd_uk.png` / `snd_sfx.png`）
   本来就在 `.mdd` 里、现在也能正常显示，所以用户看到的按钮和实际发声能对上。
2. **`snd://` 与 JS 驱动**（牛津高阶 9 的情形）：桥接里已经补上 `snd://`（不再是"未知协议一律拦掉"）；
   另外 `sound://` / `snd://` 出现在 `src`、`new Audio(...)`、`<audio src>` 里的情形，也在渲染期
   改写成 `__sound__` 路由，让词条正文自己播 —— 这样词典自带的播放逻辑同样能用。
3. **统一发音按钮**（MDict 那味儿）：读当前词条里的发音链接，按规则分出英/美：
   - 英：`GB_…`、`_gb_`、`bre…`、附近标着 BrE 的；
   - 美：`US_…`、`_us_`、`NAmE`；
   - 分不出来就按出现顺序（LDOCE5 / OALD9 都是英在前、美在后）。

   这个词条没有自带音频 → 走兜底音源。**从词条里提取比猜文件名靠谱**：
   LDOCE5 的音档名是 `GB_brelasdeapple.spx` 这种内部 ID，按词名猜不出来。

   实现落在内核：`dsh_audio_extract`（抠引用）+ `dsh_audio_classify_accent`（判口音）+
   `dsh_audio_pick`（按口音偏好挑一条，**只认词目发音，例句不算**）。

> **与原文的差异**：原文把"从词条里提取发音链接"留给了 `.mdd` 那一层，说改为"按字形 + 词典标题
> 判语种"。**现在两件事都做了、而且分工清楚**：词典自带那一层**确实**从词条里提取并判 uk/us
> （`dsh_audio.c`），语种判定（决定在线/离线用哪种嗓子）另走 `native/src/text/dsh_language.c` 的
> `dsh_language_decide`（按字形 + 词典标题）。依据：`native/src/engine/dsh_speech_api.c` 的
> `dsh_speech_plan` 第 ① 步与 `dsh_speech_dict_audio`。

### 3.4 兜底音源（"音色选择"的落点）

优先级：**本词典自带原录音（英/美）→ 在线（豆包）→ 系统离线（SAPI5）**，三层都不通时按钮置灰、
并把「缺什么」写全在 `disabledReason` 里。那一句话有个刻意的分档：本机没有这个语种的嗓子**且**
豆包也没配好时，它会拼成「本机没有X语音，豆包这条路也还没配好（…）。」——**缺什么要说全**。

- **系统离线**：`System.Speech`（SAPI5）。**壳探测音色表**（`Probe` / `VoicesJson`，探不到就回
  `null` 而不是 `[]` —— 「探不到」与「一个音色都没装」是两句话），**内核按语种 + 口音偏好挑**
  （`dsh_speech_pick_voice`）。挑不到时那句人话与设置页提示都带上"已装：无"这类现场。
  ⚠️ 「找精确地区失败就用第一个」是**刻意的**（只装了英音音色的机器上，auto 用户也得听得到英语声）——
  别因为口音偏好把发音搞没了。
  ⚠️ 英语那条地区规则里，**`auto` 也先找 `en-US`**：候选按音色名排序，直接取第一个会按字母序先撞上
  英式，于是"判不出来 → 英语兜底"这条路上报的区域（`en-US`）与实际听到的嗓子对不上。
- **在线（豆包）**：**只看"填没填 Key"，没有第二个"在线总开关"**（理由与实码见第 4 节）。
  中英混排**一律用中文音色**（实测拿英文音色念混排会得到空句子）。
- **关于 MDict 到底调的哪家服务**：它没开源，无法从本机确认；但上面这套能给出等价且可控的能力
  （统一按钮 + 音色选择 + 词典自带音频）。

## 4. 界面与设置

- **按钮**：标题栏那排加一个喇叭图标。**左键 = 念当前词条 / 播放中再点是停止**。
  播放中图标有反馈。**没有可用音源时置灰并把原因写在 `title` 上**，而不是点了没反应。

  > **与原文的差异**：原文的按钮是「左键 = 按偏好口音发音；**右键 = 小菜单**（本词典·英音 /
  > 本词典·美音 / 系统语音 / 在线·英音 / 在线·美音，带勾选）」。**那个右键菜单已经整条删掉**，
  > 理由是它两头不讨好：菜单一弹出来就按"菜单模式"把内容框收掉（用户原话的意思是"这个逻辑并不符合
  > 习惯，应该保持内容框"），而换语种这种事本来就是设置。少一个入口，"发音"就只剩一个动作：按一下念。
  > 依据：`web/src/floating/main.ts`（`dom.entrySpeak` 只有 `click`；旁边那段注释写明了删掉的理由）。
  > **音源也不给选**：顺序由内核定死，设置页里那个"默认音源"下拉框**元素本身也已经删掉**，
  > 替代品是页面顶上那段说明。依据：`web/src/manager/main.ts`。

- **管理窗的「选项」窗口 + 「语音」页签**：语速 / 音色 / 口音 / 在线那一块（Key、音色、模型版本、
  格式、响度）/ 检测凭据 / 试听 / 清空缓存，与 `settings.json` 的 `speech` 段往返。
  （最初把发音设置塞在词库列表下面做成一块可折叠区域，两个不相干的功能挤在一起、词库列表还被挤掉
  一半高度；现在是「选项」窗口 + 页签，以后加"翻译"之类只需再多一个页签。）

- **`speech` 那一节的字段**（照 `native/src/engine/dsh_settings.c` 与 `abi/lookup.abi.json` 核实）：

  | 字段 | 语义与归一化 |
  | --- | --- |
  | `rate` | 语速，**夹到 -10..10**（0 = 引擎默认）。系统离线那一层用；`dsh_speech_plan` 出的 `chosen.rate` **已经夹好**，壳不许自己去翻设置 |
  | `voiceId` | 指定的离线音色；trim 之后空 = 按语种自动挑 |
  | `accent` | **只认 `uk` / `us`，其余（含 `auto` 与脏值）一律落回 `auto`** |
  | `doubaoApiKey` | 与 `volcengine.apiKey` **同值的镜像**（见下面的「凭据」） |
  | `doubaoResourceId` | 默认 **`seed-tts-2.0`**（空 → 默认） |
  | `doubaoFormat` | 默认 **`mp3`**（空 → 默认） |
  | `doubaoSpeakerEn` / `doubaoSpeakerZh` | 豆包音色。⚠️ **空串是用户的明确选择**（「这个场景不要在线念」），**必须与"没写过这个键"分开**：`NULL` = 从来没设过 → 用内置默认音色；空串 = 留着（清空输入框保存后再打开，不该被默认值顶回来） |
  | `doubaoLoudnessEn` / `doubaoLoudnessZh` | 官方 `loudness_rate`，夹到 **-50..100**；`has_*` 记「有没有设过」—— 没设过就保持没设过 |
  | `defaultLanguage` | **读进来直接丢掉**（见下） |

  **`defaultLanguage` 是有意的行为变更**：内核把它**一律清成 NULL**、序列化时**不写**这个键，
  界面上那个「默认语种」下拉框也**整格删掉**（语种不给用户选，程序自己按词判）。
  依据：`native/src/engine/dsh_settings.c` 的 `merge_speech`（`/* defaultLanguage 读进来直接丢掉 */`）
  与 `web/src/manager/main.ts`（那一格的 change 处理器已被删掉，注释写明原因）。

- **音量增益**：两条，语义不同、谁来写也不同。
  - `speech.dictGainDb` —— **按词典存**（一本一个数），只由**用户手拖**；
  - `speech.systemGainDb` —— **全局一个**，系统离线语音那条路用。
  - 归一化：**夹到 [-24, +12] dB、取整到 0.1**（只在 `set` 那一步做）。设置页滑块的步长是 0.5 dB
    （界面显示的数就是设置里的数，写一个 −3.27 进去、用户再拖一下就跳到 −3.5，回头核对时对不上号）。
  - **`gainDb` 恒 0 的那两条路**：系统离线与在线都是**在"产字节"那一侧**施加的（合成完、交给播放器
    之前缩一遍），所以回包里的 `gainDb` 恒 0 —— **前端再乘一次就是叠两遍**。
    只有**词典自带原录音**那条是播放侧施加的（播的就是 `.mdd` 里的原字节，谁也没替它调过音量），
    而"提升"要求 `gain.value > 1`，所以播放侧得走 Web Audio 的 `GainNode`（`<audio>.volume` 上限是 1）。
  - **增益必须进缓存键**：同一个词、同一个嗓子、两个不同的音量是**两份音频**；少了它，用户拖完滑块
    再点发音会拿到上一次那份（"改了没反应"）。
  - 依据：`native/src/engine/dsh_speech_gains_api.c`、`abi/lookup.abi.json` 的
    `dsh_audio_apply_gain`，参考实现那一半对应 `GainMath.ApplyToWav`。

- **例句音频**：只响应显式点击。点它会**顶掉**正在念的词目发音（本来就该这样），
  而发音按钮的状态**只认它自己那一趟播放**（宿主记着 `ownSrc`），不会被例句的播放事件带着走。
  ⚠️ **例句录音不算词目发音** —— 统一发音按钮挑的时候**只认词目发音**
  （`dsh_audio_pick` 的硬约定），所以"这个词条只有例句录音"那一档会**正确地落空**并说明原因。

### 4.1 ★ 凭据：只存在用户自己的设置里

**这一条是工程要求，不是流程要求。**

- 程序从**用户自己的设置**里读凭据：`%APPDATA%\LookupApp\settings.json`。
  - 账号级凭据在 **`{"volcengine":{"apiKey":"…"}}`** —— **语音与翻译共用同一把 Key**；
  - **`{"speech":{"doubaoApiKey":"…"}}` 是同一把 Key 的镜像**（两个字段同值）；
  - 内核读的时候**先看 `volcengine.apiKey`，没有再退回 `speech.doubaoApiKey`** ——
    升级上来的老配置才不会丢 Key。
    （为什么必须镜像、不能各存各的：语音那条路读一个、翻译那条路读另一个，只写一边就会出现
    「语音能响、翻译说没填 Key」；而只读旧字段更危险 —— 磁盘上留着一份过期旧 Key，用户清空后重启
    又被搬回来，表现为「清不掉」。依据：`native/src/engine/dsh_settings.c` 的 `merge_speech`
    与 `dsh_settings_volcengine_api_key`。）
- **想验在线那条路的开发者，自己通过程序自己的设置页（或自己的 `settings.json`）填自己的 Key。**
  凭据的申请入口：<https://console.volcengine.com/speech/new/setting/apikeys>
- **不许写死 Key、不许提交 Key、不许编一个"看起来能跑"的占位 Key。本仓库不含任何凭据。**
- **没配 Key 时功能必须置灰 + 说明原因**，不许不报错地失败。
- 机器翻译与语音**同一把 Key、不同 `X-Api-Resource-Id`**（语音 `seed-tts-2.0` /
  翻译 `volc.speech.mt`），且**要单独开通 `volc.speech.mt` 权限**。MT 的 resource id 是**固定常量、
  不设字段、不给用户改**（与 TTS 的 `speech.doubaoResourceId` 同一个道理）。详见
  `docs/design/不带mdd的词典与机器翻译开发指导.md`。

**现实是这样（照代码写，别写成"应该"）**：

- **`dsh_settings_speech_online_ready()` 的判定只有一条：Key 非空。刻意没有第二个"在线总开关"**
  —— 多一个开关只会让用户以为"我开了在线却没走在线"。真到无网时它会失败，然后落到系统语音。
  依据：`native/src/engine/dsh_settings.c` / `dsh_settings.h`（那条注释就写在函数声明上）。
- **"这一次的覆盖"优先**：`dsh_speech_plan` 与 `dsh_speech_online_plan` 吃**同一串** `overrides_json`
  —— 两条必须看到同一份覆盖，否则会出现"规划说走在线、真发请求时却换了音色"。规则只有两条：
  **键在 = 强制这个值**（`source` 在就**只许走这一层**，那一层不可用就如实报**它自己的**原因，
  **绝不不报错地回落到别的层**）；**键不在 = 全套照设置**。
- **Key 的界面展示是掩码**：`shell/Lookup.Host/SpeechStatus.cs` 的 `Mask()` **只回前 8 后 4**
  （形如 `a30dba13…47fc`；**不超过 12 个字符**时只回一个 `…`）。**掩码是为了认，不是为了还原** ——
  完整值只有设置文件里那一份。
- **在线端点是固定常量**：`Speech.OnlineEndpoint` =
  `https://openspeech.bytedance.com/api/v3/tts/unidirectional/sse`，**不是可编辑的 URL 模板**。

  > **与原文的差异**：原文要求「在线 TTS 默认关 + **显式开关** + 首次开启时提示"会把单词发给第三方"
  > + **URL 做成可编辑模板**」，并且预置过两条实测选出的模板（有道 `dictvoice`、Google `translate_tts`）。
  > **现在这三样都变了**：① 没有在线总开关，判定只有"Key 非空"；② 端点是豆包**一个固定的流式端点**，
  > 没有模板可编辑（回包里那个 `templateIndex` 是遗留字段，**恒 -1**）；③ 服务商是豆包（火山引擎）。
  > 依据：`native/src/engine/dsh_settings.c` / `dsh_settings.h`、`shell/Lookup.Host/Speech.cs`
  > 的 `OnlineEndpoint`、`shell/Lookup.Host/SpeechStatus.cs` 的 `DoubaoView`。
  > 在线接入的完整约定（请求体、四个头、SSE 解析、错误码、为什么不写 `explicit_language`）见
  > `docs/design/豆包语音合成接入方案.md` 与 `docs/api/abi.md`。

- **翻译页缺 Key 时的做法可以照抄**：`web/src/manager/main.ts` 的 `renderTranslate()` 把三样控件
  （`translateEnabled` / `translateTarget` / `translateAuto`）置 `disabled`、**保留可见**
  （不是 `hidden`）、原因写在 `title` 上，并给一个**永远可点**的「去『语音』页填写」跳转
  —— **解锁条件本身不许被禁掉**，否则死锁。

## 6. 可移植性约束（用户明确要求：将来内核要用 C++ 重写以迁多平台）

> 这一节当初是讨论新增的**设计约束**，不是原始调研的内容。

C++ 重写那天，**会重做的只有三件**：Speex 解码器、播放器、系统 TTS；其余（资源路由、桥接改写、
前端按钮、英/美规则、设置）原样搬。所以按下面五条写，那天就是"替换"而不是"返工"：

1. **转码做成可替换的 codec 适配器**：接口定成"输入 `(字节, 源扩展名)` → 输出 `(字节, MIME)`"。
   今天注册一个 Speex 实现，将来注册 libspeex 实现、或"直通"实现。
   **任何调用方都不该知道 Speex 的存在** —— 音频路由与播放器只看见"字节 + MIME"。
2. **缓存里存"解出来的标准格式"（WAV/PCM），而不是某种语言的解码结果**；缓存键带上**解码器版本**，
   将来换实现能干净失效。
3. **播放器只接受"标准音频字节"，不接受"文件路径 + 平台假设"**：今天用 blob URL 或路由地址都行，
   但接口写成"给我字节，我来出声"。将来 macOS 换 WKWebView 时这层不用动。
4. **系统 TTS 单独隔一层，且当"可能不存在"来写**：界面写成"引擎报告可用音源列表，界面只渲染"，
   **绝不要在界面里写死 SAPI/OneCore 的假设**（macOS 是 `NSSpeechSynthesizer`、Linux 是 espeak-ng，
   枚举方式完全不同）。
5. **坚持 `<audio>` 而不是原生播放**：这条同时买下今天的体积和将来的可移植性。

**逐条对照现在的实现**（不逐条认领清楚，这五条就只是一段愿望）：

| 约束 | 现状 |
| --- | --- |
| ① codec 适配器 | **没有**单独抽一层。只有一个实现，所以接口点收敛成内核里的一个分支（`dsh_audio_prepare` 里 `.spx` 那一支 → `dsh_speex_decode_wav`）：换实现只动它，容器与 WAV 那一半不用改。等真有第二个实现时再抽不迟 —— 造一层没有第二个实现者的抽象只会多一层间接 |
| ② 缓存存标准格式 + 版本位 | **做了**，而且比原文更细：系统离线那条路的缓存键是 `sys-v1|音色|语速|语言标记|增益dB|文本` 的 SHA-256（`sys-v1` 就是那个版本位，**`gainDb` 也进键**）；在线那条是 `online-v1|请求体` 的 SHA-256（**键里不含 Key**）。存的是"能直接交给播放器的字节" |
| ③ 播放器只认字节 | **做了**：`<audio>` 只拿一条 `https://…` 地址，地址那头是本机内存缓存里的字节；`Sound` / `Speak` 两条路共用同一个出口 |
| ④ 系统 TTS 隔离 + 当"可能不存在"写 | **做了**：壳探测（`Speech.Probe`，探不到回 `null` 与回 `[]` 是两句话）、内核挑嗓子、界面只渲染内核给的人话；`Synthesize` 走 SSML、**SSML 失败就退回纯文本**（不同引擎对 `xml:lang` 与 SSML 版本的容忍度不一样，写死走 SSML 会让某些机器上一个字都念不出来） |
| ⑤ 坚持 `<audio>` | **做了**（见第 3 节那段理由） |

**一个备选打法**：把"每次播放时解码"改成"**一次性批量转码 + 缓存**"（LDOCE5 那 185,713 个键转一遍）。
好处是转完之后所有平台都只面对标准格式，C++ 那天连 libspeex 都不用链接，Speex 问题从"运行时能力"
变成"一次性数据迁移"；代价是首次转换耗时和缓存体积。**若迁移时间预期在一年内，这条路更省。**
（今天走的是"运行时解码 + 内容寻址缓存"这一条。）

> **⚠️ 磁盘缓存这一条要写准**：参考实现那一代**有落盘缓存**（`src/Audio/AudioCache.cs`，在仓库外），
> **这一版没有** —— 今天只有一个**内存**缓存（`shell/Lookup.Host/Speech.cs` 里的 `Speech.Cache`，
> 上界 64 条、先进先出淘汰）。设置页那个「清空缓存」清的就是这个内存字典，所以它**不跨重启**。

  `example`（词目发音 + 一条 LDOCE5 风格的例句音频 `p001__`）、`exampleonly`（**只有**例句录音，
  没有词目发音 ← 统一发音按钮必须落空）……加上格式矩阵 `testdata/variants/` 与清单
  `tools/golden/fixtures.txt`。**既有基线不动** —— 发音这一块有自己的一组单测；
  `tools/golden-gate.ps1`（跑当前 C 实现、与冻结基线逐字节比）该跑跑，
  但**别指望它顺带覆盖发音那条链**：它比的是解析器与词条正文，音频引用抠取的那几条断言是
  `native/tests/test_entry_doc.c` 自己钉的（那一组④）。
- **标准答案文件（golden file）**：`.spx` 的**码流是我们自己合成的**（用官方 libspeex 把我们自己
  合成的 2 秒音频编成 `.spx`）—— 既是真码流，又不牵涉词典录音的版权；**标准答案由官方实现解出**，
  正好满足"避免自己验自己"那条。`native/tests/test_audio.c` 里有一条盯着**解出来的 PCM 哈希**。
- **播放状态可断言，不靠听**：宿主页那个 `<audio>` 是挂进 DOM 的（`id="speechAudio"`、`hidden`），
  所以自动化能直接读它的 `paused` / `readyState` / `duration`。
  另外 `web/src/shared/audioGraph.ts` 在**调试钩子开着**时会把句柄挂到 `window.__speechGraph`
  （`role` / `context` / `source` / `gain` / `status()` / `tap()`），诊断可以串一个 `AnalyserNode`
  量**真的送往 destination 的那一路**的信号 —— **不许拿 `gain.value` 当检查标准**（它会跟着错误一起绿）。
- **当年列的那几条检查标准，现在各自落在哪一级**（不是删掉，是分了级）：

  | 检查标准 | 现在的落点 |
  | --- | --- |
  | `__sound__` 路由的 MIME / 长度 / 字节与 `.mdd` 内一致 | 内核单测 `test_audio` + `tools/test-windows-dll.ps1`（虚拟主机那一段验 HTTP 语义） |
  | 带 Range 回 206、越界回 416 | `tools/test-windows-dll.ps1`（`206 / 304 / 416 / 404` 那几条） |
  | 点词典喇叭后宿主 `<audio>` 真的开始播（`paused === false` / `readyState ≥ 2`） | `node tools/probe-page.mjs --speak --speak-click`（`data-played` 是 `<audio>` 的 `playing` 事件写的 —— 只有「真的开始播了」才会有，与「我们调了 `play()`」是两件事）；要看**词条里那个 🔊** 那条路就加 `--speech --speech-sound`，它还会把解出来的 WAV 头那几个数（采样率 / 声道 / 时长 / PCM 指纹）一并报出来 |
  | 统一按钮在"有音频 / 无音频 / 置灰"三种状态下表现正确 | `node tools/probe-page.mjs --speak`（读按钮的 `disabled` 与 `title` 那句人话）+ `node tools/ui-static-check.mjs`（静态那半边） |
  | 在线那条路没配 Key 时**不发出任何请求** | `node tools/probe-page.mjs --speech`（读规划里三层各自的 `available` 与 `reason`）+ 内核单测 `test_speech`（`needsHttp = false` 那一档不联网） |

- **诚实的限制**：CI / 远程会话里可能没有声卡，"真的响了"没法自动断言。
  能自动断言的是**数据通路 + 播放器状态**；最后一步"耳朵验收"留给用户，
  交付时给出具体点哪几个词的清单（`apple` / `take care of` / 一个有例句音频的词条）。
- **`--autoplay-policy=no-user-gesture-required`**：原文没提，但"查词后自动发音"（将来）与自动化验证
  都不带用户手势，不加这个开关会被 Chromium 拦掉。已经加在壳里：`shell/Lookup.App/WebViewSetup.cs`。
- **一条纪律**：新增的发音测试项**默认不属于 D 级**。加之前先回答"这条需要启动真实程序吗？"
  —— 不需要就放 B 级（内核单测），别往完整测试里塞。

## 12. 落地记录：全局兜底音源（三层里的"系统离线 + 在线"）

> 与上面各节的差异只列"实际做法和当初设想不一样"的地方。

**已经落地的**（对应第 5 节 P2/P3 里的"兜底音源"部分）：

- 触发层：标题栏那个喇叭按钮（左键发音 / 播放中再点是停止）；按钮"没有音源就置灰并把原因写在
  `title` 上"。
- 供给层：内核的规划与语种判定（`native/src/audio/dsh_speechplan.c`、
  `native/src/text/dsh_language.c`）+ 系统离线合成（`shell/Lookup.Host/Speech.cs`）+ 在线
  （`native/src/engine/dsh_speech_online_api.c` + `native/src/audio/dsh_doubao.c`）+
  两条路由（`/__speak__/` 与 `/__sound__/`，共用同一个 Range 感知的出口）。
- 播放层：宿主页一个复用的 `<audio>`（按第 6 节的约束，播放器只认"字节 + MIME"），
  增益走 `web/src/shared/audioGraph.ts`。
- 设置：**「选项」窗口里的「语音」页签**（语速 / 音色 / 口音 / 在线那一块 / 检测凭据 / 试听 /
  清空缓存 / 两条音量滑块），与 `settings.json` 的 `speech` 段往返。

**与原文设想不一样的地方（以及为什么）**：

1. **播放路由叫 `__speak__`，不是 `__sound__`。** `__sound__` 留给 `.mdd` 原录音；两者共用同一个
   Range 感知的出口（`shell/Lookup.Host/VirtualHost.cs` 的 `ServeDictSound` 与 `ServeSpeech`）。
2. **离线音源用 `System.Speech`（SAPI5），不是 OneCore/WinRT。** 三条路线都实测过：
   `System.Speech` 可用且**不增加分发体积**（框架自带、GAC 加载），而 OneCore 从 net48 调用需要额外的
   WinRT 投影，本机它的音色还全是中文。（OneCore 后来真的接了一版又撤回 —— 撤回的理由正是"本机音色
   全是中文、英文一个没有"；而"要多带一堆程序集"这条理由**实测是错的**，见第 16 节。）
3. **在线默认音源是豆包**（火山引擎的单向流式 HTTP），不是原文里那两条实测选出的模板。
4. **英/美口音不再只靠"从词条里提取发音链接"**：当时先做成"按字形 + 词典标题判语种"，
   英/美由**口音偏好**设置决定（离线挑 `en-GB`/`en-US` 音色，在线换音色 id）。
   —— 词典自带那一层的"从词条里提取"后来也补上了，两套规则**并存且分工清楚**：
   前者决定"念什么语种"，后者决定"这个词条自带哪几条录音、挑哪一条"（见第 3.3 节）。
5. **缓存键的构成**：原文说"缓存键带上解码器版本"，实际是**内容寻址的两条键**（见第 6 节那张对照表）。
6. **`Content-Length` / Range 的写法**：原文说"短音频不给 Range 也能播"，实际按规范补齐了
   （`Accept-Ranges` + 206 + Content-Range + 416）。
7. **`--autoplay-policy=no-user-gesture-required`**：原文没提，但自动化验证与"查词后自动发音"（将来）
   都不带用户手势，不加这个开关会被 Chromium 拦掉。

**明确的差异：原设计里的"默认音源可选且固定"被整个撤掉了。**
当初的做法是 `speech.preferredSource`（`auto` / `system` / `online`），而且最初右键菜单里选的音源
只对**这一次**生效，下一次点喇叭又变回自动 —— 用户看到的正是"发音过一次后又变回默认"。
后来改成"选中即写进设置、按钮从此固定走这一条"，**再后来整个下拉框与右键菜单一起删掉**：
**音源是产品约定，不给用户选**（第 3 节那条）。

## 13. `.mdd` 原录音（三层里的第一层）

**已经落地的**（第 5 节 P0 的全部内容）：

- **触发层**：词条里的 `sound://` / `snd://` / `<audio name=…>` 全接住 —— 点 🔊 就放词典自带的那一段
  （例句也算）；标题栏喇叭按钮**优先放词目录音**（按口音偏好挑英/美），这个词条没有词目录音时
  才走在线 / 系统离线兜底。
- **供给层**：内核按"词条正文 → 音频引用 → 多卷 `.mdd` 里找文件"给出键名
  （`native/src/engine/dsh_speech_api.c` 的 `dsh_speech_dict_audio`）；能播的原样透传，
  Speex 解成 WAV，认不出来如实报错（`dsh_audio_prepare`）。
- **资源路由**：两条 —— 宿主页走 `https://lookup.invalid/__sound__/<词典 id>/<键>`，
  词条正文自己播时走 `https://<词典 id>.dictres.invalid/__sound__/<键>`；两条都复用同一个出口
  （Range / 206 / 416 一次都不用重写）。
- **桥接改写**：`src` 属性与 `new Audio('sound://…')` 也一并改写，于是词典自带的播放逻辑
  （不靠 `<a>` 点击的那种）同样能用。

**与原文设想不一样的地方**：

1. **键名不能照抄 `.mdx` 里写的那个。** 原文假设"`.mdd` 里有这个键，取出来就行"；实测
   **牛津高阶第 9 版的链接写 `.spx`、音频卷里其实是 `.mp3`** —— 候选键名按
   **"常见扩展名优先（mp3/m4a/aac/wav/ogg/opus/flac）、原始键垫底"**排
   （`dsh_audio_candidate_keys`）；垫底那一条正好用来把"整本只有 Speex"如实报出来。
   内层还要再换资源键名的六种写法（`dsh_dicts_resource_key_forms`）—— 少了内层，
   键名带前导反斜杠的 `.mdd` 会一条都找不到。
2. **例句音频不需要单独路由。** 原文担心它抢统一按钮的播放；实际做法是"同一个 `<audio>`、两个用途"：
   点例句会顶掉正在念的词目发音（本来就该这样），而发音按钮的状态只认**它自己那一趟播放**
   （宿主记着 `ownSrc`），不会被例句的播放事件带着走。
3. **"这段放不了"分两处说，而且都用「内核那一句」**（没有"不报错地没反应"，也没有拿 TTS 假装顶上
   ——"显式音源只走那一条"那条规矩照旧）：
   - **点击那一刻**：宿主先拿字节整备一次（`Speech.Sound` → 内核的 `dsh_audio_prepare`），
     放不了就把内核那句话直接交给界面显示 —— 用户不用等播放器不报错地失败；
   - **路由那一头**：回 **404**，**正文就是那句话**，而且**带 CORS** —— `<audio>` 放不出来时前端会
     回头 `fetch` 这条地址把话读出来显示，少了 CORS 那次 `fetch` 会被挡掉（没声音也没说为什么）。
   依据：`shell/Lookup.Host/Speech.cs` 的 `Sound`、`shell/Lookup.Host/VirtualHost.cs` 的
   `ServeDictSound` / `NotFound`。

   > **与原文的差异**：原文（以及那一代实现）说的是"规划里标不可用 + 原因、**路由上回 415**"。
   > 现在：`dsh_audio_looks_playable` **把 `.spx` 也算作可用**（字节真到手时会解成 WAV 再发），
   > 路由上回的是 **404 + 那句人话**（不是 415）。⚠️ `.spx` **现在解得开了**，
   > 所以这条拒绝只在真正解不开的码流上才走得到。
4. **"不能放"分成四种说法**（词条没录音 / 音频卷没关联上 / 只有 Speex / 只有例句录音）。
   原文只笼统写"没有可用音源"，可这四种情形下用户要做的事完全不同。
   依据：`native/src/engine/dsh_speech_api.c` 的 `explain_no_dict_audio`。
   另外"这本词典里没有这条词条"与"词条在但没录音"也是两句话，不合成一句。
5. **多卷 `.mdd`**：原文没提，实际 `.mdd` / `.1.mdd` / `.2.mdd` … 都要找 ——
   牛津高阶的音频正好分在四卷里（每卷 5~7 万个键）。
6. **性能记账**：规划是每次查词后都要算的轻操作，所以只问"键在不在"（`dsh_dicts_mdd_contains`）、
   **不读字节**；冷启动一本大词典第一次约 160~220 ms，之后 1~11 ms。

## 14. 正文里选中文字的「朗读 / 复制」浮层

这一条**推翻了第 4 节当初的取舍**：那时按用户拍板"只做标题栏统一喇叭按钮，不做选区发音"。
后来用户明确要求补上选区朗读，于是做成"选中正文文字 → 旁边浮出 **朗读 / 复制**"，
与输入框那排浮层共用同一个元素（UI 统一）。

两个实现要点值得记在这里：

1. **选区是跨源 iframe 里的，宿主够不着** —— 由词条正文的桥接脚本上报（文字 + 选区矩形，
   节流 60ms，滚动时也报一次好让浮层跟着走），宿主只负责换算坐标与摆位。
   这也顺带解释了为什么"选区发音"当初会被排到后面：它不是触发层多做一格，
   而是**多一条跨源上报的通信桥**。
2. **朗读的音源按"选的是不是那个词"分开**：选中的正好是当前词目 → 走词典原录音；
   选了一句话 → 走在线 / 系统离线。拿"这个词"的录音去念一整句话是明确的错。
   第 3.4 节那条优先级在这里**不适用**，它管的是"念这个词"时的兜底顺序。
   依据：`web/src/floating/main.ts` 的 `speak` / `speechTarget`（选区那一趟不给词条上下文）。

## 15. Speex 解码（第 5 节 P1 的全部内容）

- **解码器在 `native/vendor/speex/`**：官方 **libspeex 1.2.1** 的解码路径，**BSD 3-Clause**，
  编进内核 DLL，**不引任何额外的原生 DLL**；容器那一半（Ogg 页/包重组、Speex 头、逐帧循环、
  WAV 封装）是自己写的 `native/src/audio/dsh_speex.c`。
- **接入点**：就在 `dsh_audio_prepare` 里（"`.spx` → 解成 WAV"），与第 6 节的安排一致；
  换实现只动 `dsh_speex_decode_wav` 这一处。
- **验收**：真实 LDOCE5 的 `apple` / `community` 都能放出原录音（**0.57 s / 1.12 s**）。
  ⚠️ 最早那版是 **0.78 s / 1.54 s** —— 慢了 **1.377 倍**，是"WAV 采样率按模式取"这个错误判断
  造成的音高偏低，**用户先听出来的**（见第 3.1 节那条坑）。
- **"逐位一致"做不到，如实记在下面**：与官方 libspeex 对照，**采样数 / 时长 / granule 完全一致**；
  实测相关系数 **1.0000**、平均样本差 **0.361**、最大差 **2**（这是内核的浮点版本）；
  参考实现那一版的 NSpeex 与官方 DLL 是 **0.978**、平均差 324。也就是说**内核这一版比参考实现更近**，
  但仍不是逐位一致（差异来自后级感知增强滤波与取整方式）。
  ⚠️ 编译参数里那个**浮点/定点开关**很关键：内核（定点）对官方 DLL 只有 0.9999、平均差 63、最大差 588。
  依据：`native/vendor/README.md` 的对照表。
- **开发期那两套对照工具没有搬进本仓库**（它们是参考实现那一代的，与那一版的 `tools/` 目录一起留在仓库外）——
  **今天这件事由内核单测接管**：`native/tests/test_audio.c` 里那条 PCM 哈希断言就是同一个检查标准，
  而且不依赖任何外部 DLL。

## 16. 撤回：OneCore（结论是**不做**）

用户先提的是「本地 SAPI5 的发音太生硬了，能否实现接入神经网络合成音源 OneCore？」，
于是真的接了一版（两套引擎、音色合并、按引擎分派、语速两套刻度都写完了），
用户听完之后的结论是**撤掉**：OneCore 在这台机器上既没有英文音色、中文音色也比 SAPI5 好不了多少
—— 也就是说，**它没解决用户抱怨的那件事**。

这一节只留三条**对将来有用的设计结论**：

1. **"音源"是路，不是引擎。** 全程守住的一条是：音源只有 `dict / online / system` 三条路，
   多一套引擎时**不要**给用户多一个 `onecore` 选项 —— 那会逼用户去理解"引擎"与"路"的区别。
   引擎差异应该落在"音色"上（选哪个音色就等于选了哪套引擎）。这次虽然撤了，
   但这套层次划分是站得住的，将来接别的引擎照用。
2. **"能接"不等于"值得接"。** 体积代价这次实测是 0（`Microsoft.Windows.SDK.Contracts` 配
   `PrivateAssets="all" ExcludeAssets="runtime"` 只提供编译期 WinMD，发布目录不多一个 DLL），
   技术上也确实跑通了 —— 但**用户要的效果一点没变**，那就不该留。
   判断"值不值得"的最终依据是**用户听到的东西**，不是"这个 API 能不能调通"。
3. **第 8 节那条体积估算要改**：原文说"引 WinRT 会带一串门面程序集"是**错的**，实测一个 DLL 都不多。
   （当时正是拿它当"不做 OneCore"的理由之一 —— 结论碰巧对，理由却是错的。）

**神经音色（Windows 11「自然语音」）依然拿不到**：它们属于讲述人体系，
没有暴露给这套普通桌面程序能用的接口。想要更自然的英文，现实路径是
①在线音源（真人录音/大模型音色）②装英文语音包 ③装第三方适配器把自然音注册成 SAPI5 音色
—— 最后这条**本程序不用改代码就能用**（SAPI5 音色是自动枚举的）。
