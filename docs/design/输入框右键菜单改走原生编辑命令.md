# 输入框右键菜单改走原生编辑命令

> 状态：**已落地** —— 悬浮窗输入框右键菜单的四项（剪切 / 复制 / 粘贴 / 全选）现在都走原生命令。
> 一句话：**不换原生菜单**，而是让自绘菜单的每一项**在底层等于对应的键盘命令** ——
> 撤销栈、`input` 事件、选区语义于是全都自动正确。
>
> 本文写的是**现在是什么样 + 为什么这么定**。四条菜单项的实现都在
> `web/src/floating/main.ts`（`cutSelection` / `copySelection` / `pasteClipboard` / `selectAllInput`），
> 那一段 `/* … */` 注释就是核心约定与实测结论的落地记录。
>
> 用词遵循 `docs/design/术语表.md`。路径一律相对仓库根（`web/…` / `shell/…` / `tools/…`）。

---

## 〇、先分清：这不是"把菜单换成系统原生菜单"

两件事很容易混，先摆清楚：

| | 换原生菜单（**不是**本文） | **本文的做法** |
| --- | --- | --- |
| 做什么 | 打开 `AreDefaultContextMenusEnabled`，让 Chromium 画菜单 | 菜单**照旧自绘**，只把**按钮的底层动作**换成原生命令 |
| 视觉 | 系统菜单，与外壳完全两套样式 | **完全不变** |
| 窗口 Region 风险 | ⚠️ 有 —— 悬浮窗是主进程用 `SetWindowRgn` 按渲染进程上报的矩形裁出来的（`shell/Lookup.App/FloatingLayout.cs:816`；界面那边为什么必须上报，见 `web/src/floating/main.ts:526` 那段注释），原生菜单若画在窗口内会被**裁掉一半**，得先实测 | ✅ 无 —— 菜单仍是 DOM，矩形照旧上报进 shape |
| 把手菜单 | 原生给不出「选项 / 重置悬浮窗位置 / 关闭悬浮窗」→ 只能自绘 → 变成混合形态（原生全局开 + 若干区域再 `preventDefault`） | **不受影响**，两个菜单继续长一样 |
| 词条正文（iframe） | 右键会弹出系统菜单，外部内容多一层系统菜单，还得单独再屏蔽 | **不受影响** |

**所以本文的做法在每个维度上都更小、更稳**，而且心智更对：用户看到的是同一个菜单，
但「剪切」这一项从此**真的就是 Ctrl+X**。

## 一、现状（已核实，带 `文件:行`）

> 行号是写作时的快照。改过代码之后**按函数名找**
> （`cutSelection` / `copySelection` / `pasteClipboard` / `selectAllInput` / `showTextMenu` /
> `openMenu`），别照抄行号。

### 1.1 原生菜单现在是整个关掉的

`shell/Lookup.App/WebViewSetup.cs` 的 `ApplySettings` 里那两行（**不相邻**，第 89 行与第 94 行）：

```csharp
settings.AreDefaultContextMenusEnabled = false; // 右键菜单由渲染进程自绘   ← :89
…
settings.AreBrowserAcceleratorKeysEnabled = false;                        // ← :94
```

这份 `ApplySettings` 是**三个窗口共用**的：悬浮窗（`shell/Lookup.App/FloatingWindow.cs:182`）、
管理窗（`shell/Lookup.App/ManagerWindow.cs:240`）、托盘菜单窗（`shell/Lookup.App/TrayMenuWindow.cs:259`）
都走 `WebViewSetup.StartAsync` —— 所以"系统右键菜单关掉"是**全程序**的一句话，不是悬浮窗特有的。

### 1.2 悬浮窗里只剩两个自绘菜单

| 菜单 | 位置 | 内容 | 能否改走原生命令 |
| --- | --- | --- | --- |
| `showTextMenu` | `web/src/floating/main.ts:2702` | 剪切 / 复制 / 粘贴 / 全选 | ✅ **本文的对象** |
| `showGripMenu` | `web/src/floating/main.ts:2750` | 选项 / 重置悬浮窗位置 / 关闭悬浮窗 | ❌ 原生没有对应物，必须自绘 |

（发音按钮那个右键菜单早先已按用户要求取消，现不存在。）
搜 `^function show\w*Menu` 命中的就是这两条；菜单容器是 `web/floating.html:146` 的 `#ctxMenu`。

### 1.3 可行的前提：**点菜单不夺焦点**

`web/src/floating/main.ts:2795-2801`（`openMenu` 里挂事件那一段）：

```ts
if (!entry.disabled) {
  item.addEventListener('mousedown', (event) => {
    event.preventDefault()      // ← 焦点留在输入框，选区也还在
    hideContextMenu()
    entry.run()
  })
}
```

`execCommand` 作用于**当前有焦点的可编辑元素**。上面这个 `mousedown` + `preventDefault()`
正是"点击不夺焦点"的标准做法。

**右键那一路还要在弹菜单之前先把光标交回输入框**（`web/src/floating/main.ts:3608-3625`）：

```ts
dom.pill.addEventListener('contextmenu', (event) => {
  event.preventDefault()
  const target = event.target as HTMLElement | null
  // 只有输入框才算"文本区"：按钮区 / 边框 / 内边距上右键不出菜单
  if (target !== dom.input) return
  dom.input.focus()
  showTextMenu(anchorOf(event))
})
```

> ⚠️ **这两条合起来才是本文可行的关键前提，改的时候一条都不许弄丢**：
> 一旦有人把菜单项改成 `click`、或者去掉 `preventDefault()`，输入框会先失焦、选区随之不可靠，
> `execCommand` 就不报错地失灵（表现成"点了没反应"，而不是报错）；
> 同理，把 `dom.input.focus()` 那一句删掉，菜单虽然照旧弹得出来，但
> "作用于焦点元素"的那几条命令会落到别处（「全选」是最容易露馅的一项，见 §八⑥）。

⚠️ **事实更正**：源文档写的是"`showTextMenu` 先 `dom.input.focus()`"（`web/src/floating/main.ts:2657`
的注释也是这么写的）—— 实际那句 `dom.input.focus()` 在**调用点**（`web/src/floating/main.ts:3623`），
`showTextMenu`（`:2702-2747`）函数体内**没有** `focus()`。
"焦点是稳的"这个结论不变，但照旧说法去函数体里找那句话是找不到的。

### 1.4 要修的缺陷：剪切 / 粘贴**不进撤销栈**

改之前的写法（在**参考实现**的 `web/src/floating/main.ts` 里；本仓库已经没有这段了）：

```ts
function cutSelection(): void {
  const { start, end } = selectedRange()
  if (end <= start) return
  const text = dom.input.value.slice(start, end)
  void api.writeClipboard(text)
  const next = dom.input.value.slice(0, start) + dom.input.value.slice(end)
  replaceValue(next, start)
  toast('已剪切')
}

function copySelection(): void {
  const { start, end } = selectedRange()
  if (end <= start) return
  void api.writeClipboard(dom.input.value.slice(start, end))
  toast('已复制')
}

async function pasteClipboard(): Promise<void> {
  const text = await api.readClipboard()
  if (!text) return
  const { start, end } = selectedRange()
  const next = dom.input.value.slice(0, start) + text + dom.input.value.slice(end)
  replaceValue(next, start + text.length)
}
```

问题出在最后那句 `replaceValue(...)` → `dom.input.value = next`：
**给 `.value` 程序性赋值不进浏览器的撤销栈**，于是——

> **右键「粘贴」之后按 Ctrl+Z 撤不回来**；而按 Ctrl+V 粘贴的**可以**撤。
> 同一个动作、两个入口、行为不一致。这正是本次要修的缺陷。

（`replaceValue()` 已经从本仓库消失：全文搜不到这个函数。它的职责由 `input` 事件 →
`onInputChanged` 接管。）

### 1.5 两条已知的"路走不通"

| 想法 | 为什么不行 |
| --- | --- |
| `document.execCommand('paste')` | **Chromium 出于安全禁止脚本发起粘贴**，永远返回 `false`（`queryCommandSupported('paste')` 也是 `false`） |
| `navigator.clipboard.readText()` | 拿不到权限。本仓库 `shell/**` 里**没有** `PermissionRequested` 处理器（搜不到），WebView2 未处理的权限请求不会给页面读剪贴板。剪贴板读数一律由**宿主**做：`shell/Lookup.App/FloatingWindow.cs:301-316` 的 `Clipboard.GetText()`（WinForms 那侧不需要浏览器权限），经 `clipboard:read`（路由表 `shell/Lookup.Host/ShellBridge.cs:900`、页面侧 `web/bridge.js:213-215`）送到界面 |

### 1.6 `execCommand` 在本仓库只出现在一个文件里

- **改动之前**：`web/**` 里搜不到 `execCommand`，也搜不到 `navigator.clipboard` —— 绿地，
  没有历史包袱，但也就没有现成经验可循（所以有了 §四 / §八那两节）。
- **现在**：`execCommand` 只出现在 `web/src/floating/main.ts`（就是本文这四个函数与它们的注释）；
  `navigator.clipboard` 仍然**一处都没有**（只在注释里提到它走不通）。

## 二、改法：逐项映射

| 菜单项 | 现在（改之前） | 改成 | 拿到什么 |
| --- | --- | --- | --- |
| **全选** | `dom.input.select()` | 用户追加要求**四项统一** → `document.execCommand('selectAll')`，并保留 `dom.input.select()` 当退路（见 §八⑥） | 四项行为一致；代价是多一层"焦点还在输入框"的前提 |
| **剪切** | 宿主写剪贴板 + 手动 `slice` 拼 `.value` | `document.execCommand('cut')` | **进撤销栈**、抛 `input`、选区语义原生 |
| **复制** | 宿主写剪贴板 | `document.execCommand('copy')` | 语义原生（现在也不算错，走原生更统一） |
| **粘贴** | 宿主读剪贴板 + 手动拼 `.value` | 宿主读剪贴板 **+** `execCommand('insertText', false, text)` | **进撤销栈**、抛 `input` |

> ⚠️ 「全选」这一行最早写的是"**可不动（已经等价）**，要统一就 `execCommand('selectAll')`" ——
> 那个"已经等价"在**本文关心的那一点上**（进撤销栈）确实成立：全选不改值，两条路都不产生撤销条目。
> 但用户后来明确要求**四项统一**，所以它现在也走原生命令。
> **它的退路比另外三项更要紧**（检查标准不能只看返回值），理由见 §八⑥ 的实测。

### 2.1 落地实现（骨架 —— 与 `web/src/floating/main.ts` 里那段一致）

```ts
/*
 * 剪切 / 复制 / 粘贴走**原生命令**（`document.execCommand`），不再自己拼 `.value`。
 *
 * 修的是什么：给 `input.value` **程序性赋值不进浏览器的撤销栈**，于是
 * 「右键粘贴之后按 Ctrl+Z 撤不回来」，而按 Ctrl+V 粘贴**可以**撤 ——
 * 同一个动作、两个入口、行为不一致。
 */
function cutSelection(): void {
  if (!hasSelection()) return
  document.execCommand('cut')
  toast('已剪切')
}

function copySelection(): void {
  if (!hasSelection()) return
  document.execCommand('copy')
  toast('已复制')
}

async function pasteClipboard(): Promise<void> {
  /*
   * 剪贴板仍由**宿主**读（`navigator.clipboard` 那条路拿不到权限，
   * `document.execCommand('paste')` 也不可用，见 §1.5）。
   * 插入则用 `insertText`：它表现得像"用户敲进去的"——替换当前选区、
   * 触发 `input`、**进撤销栈**。
   */
  const text = await api.readClipboard()
  if (!text) return
  document.execCommand('insertText', false, text)
}

function selectAllInput(): void {
  if (!document.execCommand('selectAll') || !hasSelection()) dom.input.select()
}
```

菜单那边（`web/src/floating/main.ts:2721-2744`）四项的 `run` 分别指向上面四个函数，
剪切 / 复制两项按 `hasSelection()` 置灰，四项各带 `Ctrl+X` / `Ctrl+C` / `Ctrl+V` / `Ctrl+A` 提示。

**要点**：

- `cut` / `copy` **不能** `await` —— 剪贴板类命令要用户手势，`mousedown` 给的那一次机会必须**同步**用掉。
  粘贴那条路相反：**先 `await api.readClipboard()`，再 `execCommand('insertText', false, text)`** ——
  `insertText` 不要求用户手势，所以它可以放在 `await` 之后。
  （"手势是不是 `cut` / `copy` 的必要条件"当时**没有定论**，如实记录见 §八③；
  但"有手势时确实成功"是确定的，所以约定照"必须有手势"写。）
- 剪切 / 复制**要求有选区**。判的是 `hasSelection()`（`web/src/floating/main.ts:2591-2594`，
  即 `selectionEnd > selectionStart`），与菜单项的 `disabled` 是同一句话（`:2703` / `:2727` / `:2734`）。
- `toast('已剪切')` / `toast('已复制')` 保留 —— 用户需要知道动作发生了。
  粘贴那条路**没有**提示语：文本直接进输入框，动作本身就看得见。
- 剪贴板里没有文字时粘贴**直接返回**（`:2648`）：读不到不是错误 ——
  宿主那边"剪贴板里是张图 / 刚被别的程序占着"都回空串、不抛给页面（`FloatingWindow.cs:294-300`）。
- 输入框是**单行** `<input id="input" type="text">`（`web/floating.html:118-127`），
  这决定了 §四⑤ 与 §八⑤ 那条"多行粘贴"的行为差异。

### 2.2 顺带变正确的一件事

菜单项右侧本来就写着 `Ctrl+X` / `Ctrl+C` / `Ctrl+V` 作为**快捷键提示**。
改完之后，这个提示**从"效果大致相同"变成"字面属实"** —— 菜单项真的就是那条命令。

这四条提示标出来是**如实告知，不是假快捷键**：光标在输入框里时，这四个键的剪切 / 复制 / 粘贴 / 全选
**确实生效** —— 它们是 **WebView2 对输入框的原生编辑命令**，本程序在 JS 里一个 Ctrl 键盘处理器都没有。
说明写在 `web/src/floating/main.ts:2705-2713`，删掉那个提示反而是漏信息。

> ⚠️ 别把它跟**「复制释义」那个按钮**混为一谈：那一条才是**从来没实现过**的假快捷键
> （把整条释义复制进剪贴板没有任何加速键），所以 `#entryCopy` 的提示里**不许出现 `Ctrl`**
> （见 `web/src/floating/main.ts:2715-2719`）。一处真、一处假，别一起删。

## 三、牵连清单（哪些会变死代码、哪些必须留）

| 对象 | 去向 | 依据 |
| --- | --- | --- |
| `replaceValue()` | **已整个删掉** | 它的**唯一两个调用方就是剪切和粘贴**；职责被 `input` 事件 → `onInputChanged` 接管 |
| `onInputChanged` | **确认它覆盖完整**（已核对） | `web/src/floating/main.ts:1120-1132`：`state.query` ✓ / `updateClearButton()` ✓ / 空 → 收起 + `renderEmptyHint()` ✓ / 非空 → `scheduleSuggest()` ✓。**只差 `setSelectionRange`，而原生命令自带光标** |
| `api.writeClipboard` | **不删** | 正文那排浮层的「复制」还在用它（`web/src/floating/main.ts:3064` → `web/bridge.js:216-217` → `clipboard:write`） |
| `api.readClipboard` | **要留** | 粘贴仍靠它读剪贴板（`web/bridge.js:213-215` → `clipboard:read`） |
| 后端 `clipboard:read` / `clipboard:write` | **两条都留着** | `read` 有粘贴这个用户；`write` 有**两个**用户：`writeClipboard`（正文那排的「复制」，`web/src/floating/main.ts:3064`）与 `copyText`（复制释义，`web/src/floating/main.ts:1900` → `web/bridge.js:210-211`）。路由表在 `shell/Lookup.Host/ShellBridge.cs:900` / `:903` |
| `cutSelection` / `copySelection` / `pasteClipboard` / `selectAllInput` | **保留函数名与调用点，只换实现** | 四个菜单项一行都不用动 |
| `selectedRange()` / `hasSelection()` | 换完后**回头查过调用方** | `hasSelection()` 还被 `showTextMenu` 用来算 `disabled`，保留；`selectedRange()` 现在只剩 `hasSelection()` 一个用户（`web/src/floating/main.ts:2592`） |

**`api.writeClipboard` 为什么不删**：正文那排浮层的「复制」还在用它。
那段选区住在 `sandbox="allow-scripts"` 的**跨源 iframe** 里（`web/floating.html:91-96` 的 `#entryFrame`，
opaque origin），宿主页拿不到它 —— `execCommand('copy')` 对它**没用**，只能由宿主把文本写进系统剪贴板
（`web/src/floating/main.ts:3059-3067`）。**有真实用户的桥接口，删了就是 bug。**

⚠️ **顺带纠一条容易照抄的旧理由**：旧文档写的是"`api.writeClipboard` 就算某一处已经没人用也照样不删，
理由是界面代码多版共用、桥接口保持一致比省几十行更值"。本仓库**只有一份实现**，
所以那条理由**不成立**，现在它留着的理由只有一条：**有真实用户**。
反过来也一样：哪天正文那排的「复制」被砍掉了，这条接口就该跟着一起删，
而不是靠"保持一致"挂在桥上。

### 3.1 「这是界面层唯一的实现，改它就是改全部」

`web/**` 是本程序**界面层唯一的一份实现**（与内核 `native/**`、外壳 `shell/**` 并列的那一层，
层次边界见 `AGENTS.md`）。**没有并行版本目录、没有"另一版要不要一起改"这回事**：
改它，就是改全部。

这条必须写死在文档里，因为它决定了两件事：

1. **同一个动作只能有一处实现。** 剪切 / 复制 / 粘贴 / 全选既出现在右键菜单里，也出现在键盘上
   （Ctrl+X / Ctrl+C / Ctrl+V / Ctrl+A 由 WebView2 的原生编辑命令处理，见 §2.2）。
   两处各写一份实现，就会重演本文要修的那个缺陷 ——
   **同一个动作、两个入口、行为不一致**（右键粘贴不进撤销栈，Ctrl+V 进）。
   走原生命令的价值正在这里：不是"少写几行代码"，而是**把两个入口合并成同一条命令的下游**。
2. **"改一处就行"与"只改一处就够"是两件事。** 正因为只有一份实现，任何"顺手在别处再补一份"的写法
   都是净损失：多出来的那份没有第二个版本帮我们发现它漂了。

> ⚠️ 旧文档里有一张"逐版换算表"（哪个版本行号不适用、A 级检查标准的节号是多少、
> `api.writeClipboard` 在某一版里调用方是 0 处……）。本仓库已经不再有并行版本目录，
> **那张表整表作废**；它里面唯一还成立的两条技术结论已经落到 §三（`writeClipboard` 的去留）
> 与本节（唯一实现）里。

## 四、⚠️ 只能靠真实程序量的 5 件事（量之前不许写成结论）

**整个方案的收益全押在第 ① 条上**（"进撤销栈"）。它不是读代码能确认的，必须**在真实程序里量** ——
而且它量的是"撤销栈里有没有条目"这种 **DOM 读不出来**的东西，
所以这条属于 C 级诊断脚本（probe），不是 A 级静态检查标准。

| # | 要验什么 | 为什么必须验 | 不成立时怎么办（退路） |
| --- | --- | --- | --- |
| **①** | `execCommand('insertText')` **是否真的进了浏览器撤销栈** | **这是本次改动的全部收益所在**；不进栈的话，改完和现在一样，白改 | 回退到"直接给 `.value` 赋值"的写法（功能正确，只是不进撤销栈），改为在自绘菜单里**自建撤销栈**（成本高得多，届时要重新评估值不值） |
| **②** | 编辑命令**是否抛 `input` 事件**（cut / insertText 各一次） | 决定 `onInputChanged` 会不会跑。不抛 → 切完 / 粘完**联想与「清空」按钮不刷新**、面板也不收起 | 在三个函数里手动补一次 `onInputChanged()`（显式、可读，别指望事件） |
| **③** | `cut` / `copy` 在 `mousedown` 手势内同步调用**是否成功** | 剪贴板类命令要求用户手势；菜单是 `mousedown` 接的，理论上成立，但要确认 | 若失败：保留 `api.writeClipboard` 那条路（功能正确，只是不进撤销栈），并**在注释里写明为什么** |
| **④** | 在这套 WebView2 设置下 `execCommand` 是否仍可用 | `AreDefaultContextMenusEnabled=false`、`AreBrowserAcceleratorKeysEnabled=false`（`shell/Lookup.App/WebViewSetup.cs:89` / `:94`）都是本项目特有的设置，与 `execCommand` 名义上无关，但没人在这个组合下验过 | 若不可用：整个方案作废，回退；此时才值得重新考虑"换原生菜单"那条更重的路（§〇） |
| **⑤** | **多行文本粘进单行输入框的行为差异** | `<input type="text">` 的**值净化**会删掉换行，所以"`value = a + text + b`"把 `\n` 抹成**空**；而原生粘贴路径在 Chromium 里通常是换成**空格**。这条改动**会顺带改变多行粘贴的可见结果** | 大概率是"变好"（`abc` → `a b c`）。但要**知道并接受**这个变化；不接受就只能在 `insertText` 之前自己把换行替换掉 |

### 诊断脚本（probe）该量什么（把现场交给人看）

```
· document.execCommand('insertText', false, 'X') 的**返回值**（false 就是没成功）
· 调用前后 dom.input.value 的变化
· 调用前后 **撤销栈**：做法是把值改成 A → insertText 成 B → 再 execCommand('undo')
  → 看是否回到 A。（`execCommand('undo')` 能不能用属于本项的一部分）
· 有没有 `input` 事件（挂一个一次性监听器计数）
· （⑤）分别用 "a\nb" 与 "a\r\nb" 试一次，记下最终 value
```

> ⚠️ **这份实测现在没有固化的入口**：量它的那个子命令（`--edit-commands`）在本仓库**不存在**
> （`tools/probe-page.mjs` 的固化观察里没有它），详见 §五.1。
> 这几条量法本身照旧有效 —— 缺的是"把它固化成子命令"这一步。

## 六、不要做的事

1. ❌ **不要用 `document.execCommand('paste')`** —— Chromium 禁止脚本发起粘贴，永远 `false`。
2. ❌ **不要走 `navigator.clipboard`** —— 拿不到权限（本仓库 `shell/**` 里没有 `PermissionRequested`
   处理器，WebView2 未处理的权限请求不会授权）；剪贴板一律由宿主读（`clipboard:read` →
   `FloatingWindow.ReadClipboard()`）。要开例外就得动安全设置，不值。
3. ❌ **不要把 `cut` / `copy` 放进 `await` 之后** —— 会丢用户手势。
   （`insertText` 不受此限，粘贴仍然先 `await` 读剪贴板。）
4. ❌ **不要把把手菜单（`showGripMenu`）也改走原生** —— 原生给不出
   「选项 / 重置悬浮窗位置 / 关闭悬浮窗」；而且一旦为了它打开原生菜单，
   就会连带把词条正文、标题栏按钮的右键一起放出来（§〇）。
5. ❌ **不要删 `api.writeClipboard` / 后端 `clipboard:write`** ——
   正文那排浮层的「复制」（`web/src/floating/main.ts:3064`）与「复制释义」（`:1900` → `api.copyText`）在用。
   它留着的理由**只有"有真实用户"这一条**：本仓库没有"多版本共用所以要保接口一致"那回事（§三）。
6. ❌ **不要在四个函数里"顺手"再写一次 `dom.input.value = …`** —— 那就是回到今天这个缺陷。
7. ❌ **不要把它当成"某个版本的一份实现"来改** —— `web/**` 是界面层**唯一**的实现，
   改它就是改全部；也**不要**为了"稳妥"在旁边再写一份等价实现：
   **「同一个动作、两个入口、行为不一致」正是本文要修的那个失败模式**（§一.4 / §3.1）。

## 八、实测结果（落地时量的，`--edit-commands` 输出原文）

> ⚠️ 先说清这份实测在**本仓库**的位置：量它的子命令
> `node tools/probe-page.mjs --port <端口> --match floating.html --edit-commands`
> **在本仓库不存在**（`tools/probe-page.mjs` 的固化观察里没有它，见 §五.1）。
> 下面是当时的输出原文；结论现在也落在 `web/src/floating/main.ts:2596-2624` 的注释里。
> 要重跑，先把它固化成子命令。
>
> （`userGesture: true` 就是"这次求值算用户触发的"，等价于菜单项那次 `mousedown`。）

| §四那条 | 实测结果 | 结论 |
| --- | --- | --- |
| **① 进撤销栈吗** | 值 `AAA` → `execCommand('insertText', false, 'BBB')` → 值 `BBB` → `execCommand('undo')` → **值回到 `AAA`**；对照：改用 `value = 'BBB'` → `undo` 之后**还是 `BBB`** | **进栈**。方案的核心收益成立，两个入口的行为差**被这项实测结果直接暴露出来了** |
| **② 抛 `input` 事件吗** | `insertText` 后 `inputEvents = 1`，`undo` 之后 `= 2`；对照的程序性赋值 `= 0` | **抛**。所以 `onInputChanged` 照常跑，联想与「清空」按钮不用手工补刷新 |
| **③ 手势内 cut / copy 成不成** | 都返回 `true`；`cut` 把 `hello world` 变成 `" world"`（并抛 1 次 `input`），`copy` 值不变（抛 0 次） | **成功**。留一个如实的未定论：**不给 `userGesture` 时 `cut` 也返回 `true`**，所以"手势是不是必要条件"当时**没有定论**（可能是上一次的激活还留着）；但"有手势时确实成功"是确定的 |
| **④ 这套设置下能用吗** | `queryCommandSupported`：`cut / copy / insertText / undo / selectAll` **全 `true`**；`paste` 是 `false`（如 §1.5 所述） | **可用**。`AreDefaultContextMenusEnabled=false` 与它无关 |
| **⑤ 多行粘进单行 `<input>`** | `insertText` 插 `"a\nb"` → `Xa b`（**换行变空格**）；`"a\r\nb"` → 同样 `Xa b`；`"a\tb"` → `Xa\tb`（制表符保留）。对照的老写法 `value` 拼接 → `Xab`（**换行被删掉**） | **行为确实变了**：从"直接删掉换行"变成"换成空格"，与原生 Ctrl+V 一致 —— 接受这个变化（更接近用户预期） |

**另加一条**（不在原 §四 清单里，落地时顺手量的）：菜单项的 `mousedown` + `preventDefault()`
确实让输入框**保住焦点与选区** —— 当时在真实程序里点「剪切」「粘贴」，
值分别变成 `le` 与 `aXYb`，与预期逐字相符。
（**本仓库 D 级的第 ⑭ 节不含这两条**，见 §五.1。）

| --- | --- | --- |
| **输入框有焦点**（= 菜单项的真实情形：右键时先 `dom.input.focus()`，菜单项又 `mousedown` + `preventDefault()`） | `execCommand('selectAll')` → **`true`**，输入框选区 `[0, 11]`（值 `hello world`） | 真实路径下**成立**，"四项统一"可以做 |
| **输入框失焦**（构造：`input.blur()` + `body.focus()`） | 命令**照样返回 `true`**；输入框选区也读成 `[0, 11]`；而 `window.getSelection()` 里是 `"hello world"` | ⚠️ **分不干净**：文档里唯一的文本恰好就是输入框的值，无法从实测结果上判定它选的是输入框还是整篇文档 |
| 对照：同样失焦，直接 `dom.input.select()` | 选区 `[0, 11]` | 这一句**明确指向输入框**，不受焦点影响 |

**由此定下的实现**（`web/src/floating/main.ts:2666-2668`）：

```ts
function selectAllInput(): void {
  if (!document.execCommand('selectAll') || !hasSelection()) dom.input.select()
}
```

**为什么退路判的是 `hasSelection()` 而不是返回值**：失焦那档实测**返回 true**，
所以"只判返回值"等于没判（这正是 §五 那条"钉对象、别钉替代指标"的同族情形）。
判"跑完输入框里到底有没有选区"才既覆盖"命令没跑成"，也覆盖"命令跑到别处去了"。
