# 图标设计与改进指导

> 面向**没有视觉能力**的开发模型。
> 本文的审查结论、坐标与代码都经过**真实渲染验证**（headless Edge + 看图确认），
> 除 §四 里标为"可选"的那几项之外，**请直接采用，不要重新发挥**。
> 本文同时是本仓库视觉类改动的流程依据：§〇 三条规矩、§一 的量化硬约束、§五 的三步验收、§六 不要做的事。

## 〇、给没有视觉的你：三条规矩

1. **图标是几何图形，不是文字。** 你无法"读"出它长什么样，所以**不允许凭想象判断形状对不对**。
   改完必须走 §五 的验收流程。
2. **本项目的图标就是几十个坐标点。** 形状错了不会有编译错误、不会有运行时异常 ——
   它只会安安静静地画错。所以"能编译、能运行"**不能**作为图标改对了的证据。
3. **最终验收必须由人或具备视觉能力的模型看图完成。** 你能自己做的是 §5.1 的结构自检，
   它能拦住"太阳 vs 齿轮"这类**结构性**错误，但拦不住"难看"。

## 一、图标系统现状（硬约束，先读这段再动手）

- **唯一来源**：`web/src/floating/icons.ts` 里的 `PATHS` 对象，共 **27 项**。
  其中一对是托盘菜单的 `eye` / `eyeOff`（见 §四 第 5 条）。
  每一项的值是**一段 16×16 viewBox 的原始 SVG 子元素**（`<path>` / `<circle>` / `<rect>`）。
- **统一渲染样式**在 `web/styles/tokens.css` 的 `.icon`：

  ```css
  .icon {
    width: 16px; height: 16px;
    stroke: currentColor;
    fill: none;                 /* ← 默认不填充 */
    stroke-width: 1.7;
    stroke-linecap: round;
    stroke-linejoin: round;
  }
  ```

- **关键量化约束（图标改坏最常见的根因）**：
  `stroke-width: 1.7` 占画布 16px 的 **10.6%**。
  描边会从路径向两侧各扩 0.85px，所以——
  **任何比 ≈4.2px（2.5 × 1.7）更细的细节特征都会被笔画糊掉或填平。**
- 图标名由 `IconName` 联合类型约束，`PATHS` 必须与之**一一对应**（多一个少一个都算错）。
- 改完 `icons.ts` 后**必须重新打包前端**，因为 `web/dist/*.js` 里内嵌了一份图标路径副本：

  ```powershell
  node web/build.mjs                # 只重打前端（秒级，改图标用这个就够）
  ```

  前端产物是**嵌进程序**的：要在真实程序里看图标改动的效果，还得再编一次壳：

  ```powershell
  & "$env:USERPROFILE\.dotnet\dotnet.exe" build shell\Lookup.App\Lookup.App.csproj -c Release
  ```

## 三、`gear`（「选项」）：当前实现，以及当初为什么必须这么定

### 3.1 病因（为什么会画成太阳）

它原来的结构（`icons.ts` 里已经被换掉的那一版）是：

```
<circle cx="8" cy="8" r="2.2"/>        ← 中心小圆
<path d="M8 1.6v2.2"/>                 ← 向上的短线段
<path d="M8 12.2v2.2"/>                ← 向下
<path d="M1.6 8h2.2"/> ...             ← 共 8 根"两点一线"的放射短线
```

"中心一个小圆 + 8 根放射短线" = **太阳**。这是刻在所有人认知里的字形，没有任何歧义。

而原代码注释写的是"内圆 + 八根短齿"——这个说法在几何上**不成立**：
**它只有"辐条"，没有"齿"的身体（实体块）。** 齿轮的辨识特征恰恰是
**外面一圈带豁口的实体齿圈 + 中心的孔**。所以它读作太阳是必然结果，不是画得不够好。

### 3.2 为什么**不能**继续用"描边"画齿轮（实测过，别再试了）

当时按 6 齿 / 8 齿 / 5 齿、不同齿高试了 5 种**描边**齿轮，真实渲染结果：

| 齿高 | 实测结果 |
| --- | --- |
| 1.9px（≈ 笔画宽 1.7） | **退化成实心圆环**：齿顶与齿根的笔画互相吃掉，只剩 0.2px 起伏，完全看不出齿 |
| 3.2px（齿拉很高） | **退化成雪花 / 星号**：齿变得细长，16px 下糊成辐射状，比原来的太阳更像太阳 |
| 加粗齿宽（仍描边） | 依旧是星号 |

原因就是 §一 那条约束：要让齿看得见，齿高至少要 ≥ 2.5 × 1.7 ≈ **4.2px**；
而画布只有 16px，还要塞下中心孔 —— 根本放不下。

> **结论：在这个 stroke-width 下，描边画不出齿轮。改成实心是唯一稳妥的路。**

### 3.3 当前实现（方案 A）：实心 6 齿

`PATHS` 里 `gear:` 那一项**现在的形状**（已经落地）：

```ts
  gear:
    '<path fill="currentColor" stroke="none" fill-rule="evenodd" d="M6.23 1.12L9.77 1.12L9.42 3.31L11.35 4.43L13.07 3.03L14.84 6.09L12.77 6.88L12.77 9.12L14.84 9.91L13.07 12.97L11.35 11.57L9.42 12.69L9.77 14.88L6.23 14.88L6.58 12.69L4.65 11.57L2.93 12.97L1.16 9.91L3.23 9.12L3.23 6.88L1.16 6.09L2.93 3.03L4.65 4.43L6.58 3.31Z M5.5 8a2.5 2.5 0 1 0 5 0a2.5 2.5 0 1 0 -5 0Z"/>',
```

**当初为什么必须定成这个形状**：§3.1 说明"太阳"是必然结果、不是画得不够好，
§3.2 又实测证明在本套笔宽下描边画不出齿轮 —— 两条加起来，只剩"实心"这一条路。
所以这两节里的技术理由一条都没有过期：改这个图标之前先把它们读完。

**三个属性缺一不可，这是最容易踩的坑：**

| 属性 | 作用 | 漏了会怎样 |
| --- | --- | --- |
| `fill="currentColor"` | 填充成实心 | 被 `.icon { fill: none }` 继承，**画出来是空的（什么都看不见）** |
| `stroke="none"` | 关掉这个图标的描边 | 1.7 的描边会把齿缝糊掉，实心齿轮退化成"圆环 + 毛边" |
| `fill-rule="evenodd"` | 用奇偶填充规则 | 第二条子路径（中心孔）**填不上洞**，变成实心饼 |

几何参数（以后要微调就改这几个数，再用 §3.4 的公式重算）：

| 参数 | 取值 |
| --- | --- |
| 齿数 N | **6** |
| 齿顶半径 R | **7.1** |
| 齿根半径 r | **4.9** |
| 齿顶半宽 | **0.24 × 齿距** |
| 齿槽起点 | **0.28 × 齿距** |
| 中心孔半径 | **2.5** |

**为什么是 6 齿**：16px 下**齿越少、齿越粗**，越不会被糊成一团。
实测 6 齿在 16px 最清楚；8 齿偏细，5 齿开始像"加号外面套个圈"。

### 3.4 生成公式（要调参数时用这段，别手算坐标）

```js
/** 0° = 正上方，顺时针 */
function polar(r, deg) {
  const a = ((deg - 90) * Math.PI) / 180
  return [8 + r * Math.cos(a), 8 + r * Math.sin(a)]
}

/**
 * 直齿外轮廓：每齿 4 个点（齿顶起点、齿顶终点、齿根起点、齿根终点）。
 * tipHalf / valley 都是"齿距的几分之几"，保证左右对称。
 */
function gearOutline(N, R, r, tipHalf, valley) {
  const pitch = 360 / N
  const pts = []
  for (let i = 0; i < N; i++) {
    const th = i * pitch
    pts.push(polar(R, th - tipHalf * pitch))
    pts.push(polar(R, th + tipHalf * pitch))
    pts.push(polar(r, th + valley * pitch))
    pts.push(polar(r, (i + 1) * pitch - valley * pitch))
  }
  return `M${pts.map((p) => `${p[0].toFixed(2)} ${p[1].toFixed(2)}`).join('L')}Z`
}

/** 圆（用来挖中心孔，配合 fill-rule="evenodd"） */
function circlePath(cx, cy, r) {
  return `M${cx - r} ${cy}a${r} ${r} 0 1 0 ${2 * r} 0a${r} ${r} 0 1 0 ${-2 * r} 0Z`
}

// 方案 A：
const gear = `<path fill="currentColor" stroke="none" fill-rule="evenodd" d="${
  gearOutline(6, 7.1, 4.9, 0.24, 0.28)
} ${circlePath(8, 8, 2.5)}"/>`
```

## 四、其它图标（可选，非必须）

1. **`text`：已不存在。** 本仓库核实：`icons.ts` 的联合类型与 `PATHS` 里都搜不到 `text`
   （全 `web/` 搜 `'text'` 只命中 `web/src/manager/main.ts` 的 `input.type = 'text'`）。
   这条"建议删除"已经**作废** —— 东西早就没了，**别再照它去"删两处"**。
2. **`selectAll`：语义建议对齐。** 现在"圆角方框 + 对勾"
   （`<rect x="2.6" y="2.6" width="10.8" height="10.8" rx="2"/>` + 一条对勾）读作"已完成"，
   用在「全选」上不对。
   若改，推荐"虚线框 + 框内三行短横线"；或最省事的做法是这一项直接复用 `check`。
   **不改也不算错** —— 用户当时只说了齿轮。

   （全 `web/` 搜 `globe` 零命中），所以原文对它的"16px 下是外圆 + 赤道 + 两条经线"的描述
   已经无从对应；"若要减负去掉一条经线"这条建议随之**作废**（**没有对象可改**）。
4. **`clearInput`（清空输入）：已经改过一次，不再是退格键。**
   它的前身是 `backspace`（五边形外框 + 里面一个小叉），**翻车原因与 `gear` 同源**：
   那个叉只有 2.8px 长，比"最小可辨特征" 2.5×1.7≈4.2px 还小，16px 下糊成一坨墨；
   实测**把叉撑到几何极限（4.0px）照样糊** —— 说明"外框 + 内小符号"这个两层结构
   在本笔宽下根本装不下，于是整条路放弃，改成**一个不套容器的小叉**
   （跨度 7.2px、`stroke-width="1.4"` 写在 path 的 presentation attribute 上，
   按 `close` 的 8.8px @ 1.7 等比缩小）。
   **现状核实一致**：`PATHS.clearInput` 就是两条 `<path stroke-width="1.4" d="M4.4 4.4 11.6 11.6"/>`
   这样的斜线，外面没有任何外框。
   上一代实现**仍是退格键**（五边形外框那一版），它的 A 级检查标准钉着"五边形 + 两条交叉线段"——
   但那是上一代的事，与本仓库无关。**本条就是完整的论证，别再改回去。**
5. **`eye` / `eyeOff`（托盘菜单的显示 / 隐藏悬浮窗）**：托盘菜单原来两个状态共用 `search`（放大镜）。
   后来拍板改成一对眼睛：`eyeOff`（眼形轮廓 + 实心瞳孔 + 一条 45° 斜线）= 「隐藏悬浮窗」，
   `eye` = 「显示悬浮窗」。**瞳孔必须是实心块**（`fill="currentColor"` + `stroke="none"`）：
   少了 fill 会被 `.icon{fill:none}` 继承成空形状，写成描边圆则会在 16px 下糊成一个点
   （比最小可辨特征 4.2px 还小；实心块不受这条约束 —— 尺寸再小也是干净的形状）。
   **现状核实一致**：`PATHS.eye` 是"上下两条对称的弧拼成的眼形轮廓 + `fill="currentColor" stroke="none"`
   的瞳孔"，`eyeOff` 在它的基础上多一条 `M3.6 12.8 12.4 3.2` 的 45° 斜线。
   ⚠️ 与「最小化到托盘」那个 `toTray`（箭头落进托盘）**不是同一套符号**，两者动作很接近 ——
   选眼睛对就是接受了这一点；`toTray` 的形状是既定的、**不许顺手改**，要统一两者得单独做一次改动。

## 五、验收流程（你无法用眼睛验收，照这个来）

### 5.1 第一步：结构自检（你自己就能跑，不需要视觉）

⚠️ **本仓库目前没有 `tools/icon-check.mjs` 这个文件**（`tools/` 下逐个查过，没有它）。
下面这段是**结构自检的规格** —— 它是本文的核心资产（判得动"太阳 vs 齿轮"这种结构性错误）：
**需要的时候照它建到 `tools/icon-check.mjs`**。脚本里那句
`new URL('../web/src/floating/icons.ts', import.meta.url)` 正好是从 `tools/` 指向
`web/src/floating/icons.ts`，所以**文件必须放在 `tools/` 下**，别挪位置。

```js
// 图标自检：不需要视觉能力，纯结构断言。
// 用法: node tools/icon-check.mjs
import fs from 'node:fs'

const FILE = new URL('../web/src/floating/icons.ts', import.meta.url)
const src = fs.readFileSync(FILE, 'utf8')

const names = [...src.matchAll(/^\s*\|\s*'([A-Za-z]+)'/gm)].map((m) => m[1])
const bs = src.indexOf('{', src.indexOf('const PATHS'))
let depth = 0
let end = -1
for (let i = bs; i < src.length; i++) {
  if (src[i] === '{') depth++
  else if (src[i] === '}') { depth--; if (depth === 0) { end = i; break } }
}
const PATHS = new Function('return (' + src.slice(bs, end + 1) + ')')()

let fail = 0
const ok = (cond, msg) => { if (!cond) { console.log('  ✗ ' + msg); fail++ } }

// 1) 名字与实现一一对应
for (const n of names) ok(PATHS[n], `联合类型里有 ${n}，但 PATHS 里没有`)
for (const k of Object.keys(PATHS)) ok(names.includes(k), `PATHS 里有 ${k}，但联合类型里没有`)

// 2) 只允许 path / circle / rect（不许 <text>、<g>、字体、外链）
for (const [n, d] of Object.entries(PATHS)) {
  const tags = [...d.matchAll(/<([a-zA-Z]+)/g)].map((m) => m[1].toLowerCase())
  for (const t of tags) ok(['path', 'circle', 'rect'].includes(t), `${n} 用了不允许的元素 <${t}>`)
  ok(!/style\s*=|url\(|href/i.test(d), `${n} 里出现了 style/url/href`)
}

// 3) gear 专项：必须是"实心齿轮"，不能退化成"太阳"
const gear = PATHS.gear || ''
console.log('gear 专项检查:')
ok(/fill="currentColor"/.test(gear), 'gear 缺少 fill="currentColor"（否则会被 .icon 的 fill:none 变成空形状）')
ok(/stroke="none"/.test(gear), 'gear 缺少 stroke="none"')
ok(/fill-rule="evenodd"/.test(gear), 'gear 缺少 fill-rule="evenodd"（中心孔挖不出来）')

const subpaths = [...gear.matchAll(/<path[^>]*\sd="([^"]*)"/g)].flatMap((m) =>
  m[1].split(/(?=M)/).filter((s) => s.trim())
)
ok(subpaths.length === 2, `gear 应该是 2 条子路径（外轮廓 + 中心孔），实际 ${subpaths.length}`)

const holes = subpaths.filter((s) => /a[\d.\s]+0\s+1\s+0/.test(s))
ok(holes.length === 1, `gear 应该有且仅有 1 个圆形孔，实际 ${holes.length}`)

const toothPoints = (subpaths[0] || '').match(/L/g) || []
ok(toothPoints.length >= 20, `gear 外轮廓的折点数偏少（${toothPoints.length}），不像带齿的轮廓`)

// 太阳的特征：一堆"两点一线"的独立放射短线段（不含 L / a / C）
const stubs = subpaths.filter((s) => {
  const body = s.replace(/^\s*M/, '')
  return !/[LaCcSsQqTt]/.test(body) && body.length <= 24
}).length
ok(stubs === 0, `gear 里有 ${stubs} 根独立放射短线段 —— 这正是"太阳"的画法`)

console.log(fail === 0 ? '\n全部通过' : `\n${fail} 项未通过`)
process.exit(fail === 0 ? 0 : 1)
```

### 5.2 第二步：出图（用于交人确认）

本机有 headless Edge，`--force-device-scale-factor` 是**关键**：
16px 的图标必须放大到 128px 像素来出图，否则图上根本看不出"是齿轮还是太阳"。

```powershell
& "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe" `
  --headless=new --disable-gpu --hide-scrollbars `
  --force-device-scale-factor=8 `
  --screenshot="out.png" --window-size=650,125 `
  "<指向 preview.html 的 file:// URL>"
```

`preview.html` 里放一段只含图标的静态页（自己写一份放在临时目录即可），
**并且必须复制 `.icon` 的真实 CSS**
（`fill:none; stroke:currentColor; stroke-width:1.7; stroke-linecap:round; stroke-linejoin:round`），
否则渲染出来的不是程序里的样子。

**本仓库里现成的出图 / 核对手段**（下面这几个入口都真实存在，优先用它们）：

| 手段 | 用途 |
| --- | --- |
| `node tools/probe-page.mjs --shot <文件>` | 对着**跑起来的程序**出图（CDP 截图，窗口在屏幕外也能拍）。配套：`--shot-hover <选择器>` 先拍 `:hover` 态，`--shot-scale N` 整页放大 N 倍再拍 |
| `powershell -NoProfile -ExecutionPolicy Bypass -File tools\make-screenshots.ps1` | 批量出 README 用的产品截图，默认写到 `release/screenshots/`（用 `testdata/` 的冻结测试用词典 + 临时配置目录，不碰开发者本人的配置） |
| `node tools/diff-png.mjs <a.png> <b.png> [--rows]` | 两张 PNG **逐像素比** —— "落地后的渲染"与"给人看过的那张图"是不是同一张，靠它判，不靠人眼 |
| headless Edge `--force-device-scale-factor` | 把 16px 图标放大到 128px 出图（上面那段命令），专门用来看清笔画细节 |

⚠️ `--shot-scale` 在隐藏窗口（`--no-show`）下会挂住（`Emulation.setDeviceMetricsOverride` 之后
`Page.captureScreenshot` 一直不返回）—— 细节见 `tools/probe-page.mjs` 里的说明。

值得出图的三种视角：
1. **真实尺寸**（16px 放进 32px 圆钮）—— 判断"能不能认出来"；
2. **放大**（64px）—— 判断"形状对不对"；
3. **放进真实菜单**（图标 + 文字并排）—— 判断"视觉重量是否突兀"。
   当初就是靠这一步发现"实心齿轮在菜单里并不突兀，而描边齿轮看起来像雪花"。

### 5.3 第三步：交人看图（不可省略）

明确问一句：**"这个像齿轮吗？"** —— 得到肯定答复才算完成。

## 六、不要做的事

1. **不要改 `.icon` 的全局 `stroke-width`。** 它被全部 **27** 个图标共用，动一下整套都会变。
2. **不要用 `<text>`、字体图标或外部图片。** 图标必须是纯几何路径
   （本仓库目前没有结构自检脚本；照 §5.1 的规格建好 `tools/icon-check.mjs` 之后由它拦）。
3. **不要引入任何依赖。** 这个项目连测试框架都不装，图标是手写坐标。
4. **不要给其它图标单独加 `stroke-width` 覆盖。** 除非是 §3.6 那种明确要求"整套保持只描边"的情况。
5. **不要"顺便美化"其它图标。** 只动确有必要、且经确认的那几项（§四）。
6. **不要忘记重新打包前端。** 改完 `icons.ts` 要 `node web/build.mjs`，
   否则 `web/dist/*.js` 里还是旧图标（那份是内嵌副本，不会自动跟着源文件走）。
