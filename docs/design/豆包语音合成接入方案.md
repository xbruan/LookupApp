## 〇、开工前（**硬性前置**）

**不要猜、不要用默认值硬跑、不要写完代码才第一次发请求。**
这一步缺了，只能空转或者交付一段跑不通的代码。

### ① 凭据由程序从**用户自己的设置**里读

**本仓库不含任何凭据**，本文也不出现任何凭据。想动在线那条路的开发者，
**自己通过程序自己的设置页（或自己的 `%APPDATA%\LookupApp\settings.json`）填自己的 Key** ——
把「要验在线那条路」当成自己的环境准备，不是向别人索要。

- 账号级凭据住在 `{"volcengine":{"apiKey":"…"}}`；**语音与机器翻译共用同一把**。
- `{"speech":{"doubaoApiKey":"…"}}` 是**同一把 Key 的镜像**（两个字段同值，一起写一起清）。
  内核读的时候**先看 `volcengine.apiKey`，没有再退回 `speech.doubaoApiKey`** ——
  升级上来的老配置才不会丢 Key；`native/src/engine/dsh_settings.c` 里那段 `touch_mirror` 就是它，
  它还有一条补丁语义：**两个 Key 字段都没在补丁里出现时，镜像不能动**
  （否则「只改语速」的补丁会把已填好的 Key 抹掉）。
- **不许写死 Key、不许提交 Key、不许编一个「看起来能跑」的占位 Key。**
- Key 在设置文件里是**明文**（与其余设置同库同明文，个人桌面程序可接受），
  所以界面上要写明这一点，并提醒别把这个文件外发。
- 界面上 Key 是**掩码**：`shell/Lookup.Host/SpeechStatus.cs` 的 `Mask()` **只回前 8 后 4**，
  形如 `a30dba13…47fc` —— 掩码是为了**认**（"我填的是哪一把"），不是为了还原；
  完整值只有内核 / 设置文件里那一份，界面输入框平时是空的、只把掩码当占位符。
- 缺凭据时**界面不许自己编话**：那句「还没有填 API Key（在「设置 → 语音」里填，旁边写着怎么申请）」
  由内核给（`native/src/engine/dsh_speech_api.c` 的在线那一层），界面原样显示。

**「检测凭据」按钮会真联网、按字符计费**，所以**只由用户点按钮触发**。
它落在 `shell/Lookup.Host/Speech.cs` 的 `TestDoubao`、由
`web/src/manager/main.ts` 的 `api.testDoubao()` 调用；`web/manager.html` 里那个按钮
「一个按钮两行字」（语音合成 + 机器翻译各一行），并且**刻意绕开翻译缓存** ——
走缓存的话，Key 被撤销了照样报 ✓。

### ② 音色（**要让用户挑，不要替他决定**）

**不要只丢一句「把音色 ID 给我」**，也不要让他自己去翻音色列表。
直接把候选摆出来让他选（见 §6.6）：

- **英文音色**（词典主要念英文单词）—— 选一个；
- **中文音色**（汉语词条 / 中文释义朗读 / **中英混排**）—— 选一个。

两个格子都可以留空：留空就用**内置默认音色**
（`native/src/audio/dsh_doubao.h` 的 `DSH_DOUBAO_DEFAULT_SPEAKER_EN` /
`DSH_DOUBAO_DEFAULT_SPEAKER_ZH`，界面上显示的是内核给的官网名 `Dacey` / `Vivi`）。
**只配英文音色也能出声**：中文音色留空时，中文与混排会回落到英文音色
（`dsh_doubao_speaker_for`，§6.1），功能不会缺。

### ③ 为什么是「中英各一个音色」

早期方案定的是**单音色** `zh_female_vv_uranus_bigtts`，靠 `explicit_language` 自动切中/英。
查音色表后发现两个问题：

1. **Vivi 2.0 的多语种列表是「中文 / 日文 / 印尼语 / 西班牙语」——不含英语。**
   用它念英文单词效果存疑（§9.2 实测：确实会念出声，只是好不好听要人耳判）。
2. 2.0 音色里**本来就有专门的英文音色**（`en_*_uranus_bigtts`），
   而词典念的绝大多数是英文单词。

所以改为**中英各配一个音色**：

- 收益：英文单词的发音质量（部分 2.0 中文音色的多语种列表里**并不含英语**）；
- 代价：设置里多一个音色输入框。

### ④ 拿到凭据之后：**先验证，再写代码**

```powershell
# 1) 单次基本连通性
node tools/probe-doubao.mjs --api-key <你的 key> --speaker <音色ID> --text apple

# 2) 中英混排专门测试（5 次请求，各存一个 mp3）—— 顺便把音色定下来
node tools/probe-doubao.mjs --api-key <你的 key> --mixed-test
```

打印状态码 / 耗时 / 字节数 / 错误码，并把音频存成 `.mp3` 供**当场试听**。

**第 2 步不是可选项**：词典正文是中英混排的（`apple 苹果，一种水果`），
而 `explicit_language` 是"只念这个语种"的**限制**而非提示（§2.2 / §6.1）。
不先跑它，就会交付一个"点朗读只出声念了英文"的 bug。规格见 §8.1。

> `tools/probe-doubao.mjs` 是本仓库里**独立、可单独运行**的诊断脚本（规格见 §八）。
> 理由：这是**全程序唯一会联网的付费接口**，必须在写业务代码之前先有一个能独立验证它的工具，
> 也让用户能在界面上线之前就听到声音、把音色定下来。
>
> **为什么必须先验通再写 provider**：没有它，第一次真实请求会发生在
> "业务代码写完、跑起来、点发音"那一刻 —— 失败时你分不清是 Key 错了、服务没开通 / 权限没开、
> 音色 ID 或语种代码不对、还是 SSE 解析写错了。有了它，这几件事被摊在几个独立步骤里逐个排除。
>
> **同样重要的一条：不要不报错地失败。** 服务端会回 `code 0` + 零字节音频
> （最典型的成因就是"拿英文音色念中英混排"，见 §9.2），所以
> **"真正拿到了非空音频"才算成功，"请求成功"不算证据**；同理，
> 缺凭据 / 没配音色时要把那一条**置灰并说明原因**，而不是让用户点了没声音、也没有提示。

### ⑤ 没配凭据 / 没配音色时怎么办

| 情况 | 处理 |
| --- | --- |
| 有 Key，没配音色 | 两个音色格都留空时用**内置默认音色**（`DSH_DOUBAO_DEFAULT_SPEAKER_EN` / `_ZH`）先跑通，并在界面上写明**用的是哪个、怎么换** |
| 完全没有 Key | **禁止写死占位 Key 假装能跑**。配置项与界面照做，缺 Key 时「豆包语音（在线）」那一条**置灰并说明原因**：`dsh_speech_api.c` 里在线那一层的 `available=false` + 那句「还没有填 API Key（在「设置 → 语音」里填，旁边写着怎么申请）」；`dsh_speech_online_plan` 的 `no-key` 那一档另有一句同义的人话（「在线发音需要火山引擎凭据（与机器翻译共用同一把 API Key）—— 先去「语音」那一页填上。」）。界面**原样显示内核给的话**，不自己另编。置灰而**不是藏起来** —— 藏起来等于把"为什么不能点"一起藏掉 |
| 音色没填 / 没配齐 | 内核把**「没东西可测」与「服务端说它不能用」分开说**（`dsh_speech_online_test_plan` 每一项的 `reason`），界面不许把两档混成一句 |
| 403 / 鉴权失败 | 提示「API Key 不对，或者语音服务没开通 / 实名认证没做完」（§2.4 那张表） |
| `45000030` / `requested resource not granted` | 提示「这个音色 / 服务没在当前账号下开通：去控制台开通服务，并在音色管理里开启要用的**试用音色**」——**Key 本身是有效的**，这不是代码问题 |
| 报 quota / 用量用完 | 提示「试用额度已用完，需在控制台开通正式版」 |

### ⑥ 没有第二个「在线总开关」

`dsh_settings_speech_online_ready()`（`native/src/engine/dsh_settings.c`）的判定**只有一条：Key 非空**。
**刻意没有**第二个"在线总开关"—— 多一个开关只会让用户以为「我开了在线却没走在线」。
在线那一层能不能走，在 `dsh_speech_api.c` 里也是**只看 Key 有没有填**（外加"有没有要念的文本"）。

这一条与翻译那一页**不是**同一套：

- `translate.enabled` 是**用户自己的开关**、**默认 false**（要联网、要把文本发给第三方，得用户主动打开）；
  `abi/lookup.abi.json` 里 `dsh_translate_status` 的注释明写
  「`enabled`（用户自己的开关）与 `hasApiKey`（凭据有没有）**必须分开判**」。
- 翻译页缺 Key 时把三样控件（`translateEnabled` / `translateTarget` / `translateAuto`）置 `disabled`、
  **保留可见**（不是 `hidden`）、原因写在 `title` 上，并给一个**永远可点**的
  「去『语音』页填写」跳转（`web/src/manager/main.ts` 的 `renderTranslate`）——
  解锁条件本身不许被禁掉，否则死锁（没 Key 就填不了 Key）。

## 一、已拍板的设计决定

| 问题 | 决定 |
| --- | --- |
| 豆包的角色 | **「在线语音」就是豆包**：不再保留有道 / Google 的 URL 模板作为主在线音源 |
| 音源优先级 | **词典自带音频 → 豆包(在线) → 系统语音**。豆包严格排第二；只有无网络 / 豆包不可用时才退回到系统语音 |
| 音色 | **中英各一个音色**（见 §〇 ③ 的修正说明） |
| **`explicit_language`** | **请求体里一个字都不传**（= 官方"正常中英混读"），并用**支持中英混读的音色**。<br>**绝不能按"检测到的主语种"传这个参数** —— 它的语义是"只念这个语种"，那会让另一语种被跳过甚至整条失败。见 §6.1 |
| **中英混排走哪个音色** | **走中文音色**（§9.2 实测：英文音色念混排回 0 字节、而且不报错） |
| 声音复刻 | **不做**。只用 2.0 音色、Resource ID 恒定 `seed-tts-2.0`；`S_` 开头那种复刻音色不在本项目的范围里 |
| 语音指令 `context_texts` | 见 §9.6：**产品代码不转发它**；这个字段只在诊断脚本里量 |
| 模型版本 | 与音色**必须配套**（§2.3）。界面上那一格是**只读**的，不给用户改 |

音源顺序是**产品约定**，住在内核里（`native/src/engine/dsh_speech_api.c` 排
`dict → online → system` 三层，连每一层为什么通/不通的人话都在里面），
**界面不给选、也不许自己判**（`dsh_speech_plan` 的接口注释写着这一条）。

这个决定带来一个直接好处：**不需要**再引入独立的 `readAloudSource`（朗读首选音源）。
因为「选中朗读」念的是任意文本、永远命不中词典原录音，所以
`dict → 豆包 → system` 这一条链自然满足两个诉求：

- 单词发音：有原录音放原录音，没有就豆包，再不行系统语音；
- 选中朗读：`dict` 那层天然跳过，豆包自动成为首选，无网才降系统语音。

### 「音色」这一行的修正说明（查证音色表后）

原方案定的是**单音色** `zh_female_vv_uranus_bigtts`，靠 `explicit_language` 自动切中/英。
查音色表后发现两个问题：

1. **Vivi 2.0 的多语种列表是「中文 / 日文 / 印尼语 / 西班牙语」——不含英语。**
   用它念英文单词效果存疑。
2. 2.0 音色里**本来就有专门的英文音色**（`en_*_uranus_bigtts`），
   而词典念的绝大多数是英文单词。

所以改为**中英各配一个音色**。只配一个也能跑：中文音色留空 → 中文与混排回落到英文音色
（`dsh_doubao_speaker_for` 里那一格回落）。

## 二、调研结论（豆包 API 现状）

豆包语音 = 火山引擎「语音合成大模型」，产品线叫 seed-tts。分两代接口：

| | 鉴权 | 形态 | 现状 |
| --- | --- | --- | --- |
| **V3**（采用） | 新版控制台 **API Key**（单个 `X-Api-Key` header） | HTTP Chunked / **SSE** / WebSocket | 当前主推 |
| V1（历史） | appid + access_token + cluster + **HMAC-SHA256 签名** | 非流式 HTTP | 已入「历史文档」，不用 |

**采用 V3 的 SSE 单向流式**（一次 POST 输入文本，流式返回音频），理由是：

- 鉴权最简单（一个 API Key header，无需 HMAC 签名、无需 APP ID）；
- 返回 mp3，正好复用现成的音频暂存与 `<audio>` 播放；
- 单次请求即可覆盖「单词」到「300 字朗读分段」的全部场景，无需 WebSocket 长连接。

### 2.1 开通流程（官方约定，约 5~10 分钟）

```
注册账号 → 开通服务 → 创建 API Key → 填进设置 → 调用
 (1 次)     (1 次)       (1 次)         (1 次)     (随时)
```

1. **注册** <https://www.volcengine.com>（手机号，或抖音/飞书等第三方登录）；
2. **首次登录控制台需完成实名认证**（不做的话后面开不了服务）；
3. **开通服务**：<https://console.volcengine.com/speech/new/setting/apikeys>，按页面引导开通；
4. **创建 API Key**：同一页面点【创建 API Key】，复制。

> ⚠️ 网上很多教程还在讲 `APP_ID + Access Token` —— 那是**旧鉴权**。
> 新版控制台只要一个 API Key，别被带偏。
>
> **同时要确认两句话**：「服务开通了吗？」「实名认证过了吗？」
> —— 这两件没做的话，Key 拿在手里也会被拒（表现见 §2.4 的 `40300001` 与
> `45000030 requested resource not granted`）。
>
> 这四步的出处是 ByteDance 官方示例仓库里的开通指南：
> [agentkit-samples · byted-text-to-speech · setup-guide.md](https://github.com/bytedance/agentkit-samples/blob/main/skills/byted-text-to-speech/references/setup-guide.md)

### 2.2 接口要点

**端点常量住在 `shell/Lookup.Host/Speech.cs`**（`OnlineEndpoint`），内核那一半是
`native/src/audio/dsh_doubao.h` 的 `DSH_TTS_ENDPOINT` —— 两边是同一个地址：

```
POST https://openspeech.bytedance.com/api/v3/tts/unidirectional/sse

请求头（**四个头 + 一个计费开关**，由内核拼好交给壳原样发出去）：
  Content-Type: application/json
  X-Api-Key: <用户自己在设置里填的那把 Key>
  X-Api-Resource-Id: seed-tts-2.0          # 模型版本，**必须与音色配套**（见 2.3）
  X-Api-Request-Id: <uuid 形状，每次一个>   # 服务端排错要用（壳/脚本不自己编，内核生成）
  X-Control-Require-Usage-Tokens-Return: *  # 设为 * 才会返回计费字数（响应里的 usage.text_words）

请求体（**本项目自己必须决定的那几层**：`user.uid`、`req_params`、`audio_params`、`additions`）：
{
  "user": { "uid": "lookup" },
  "req_params": {
    "text": "apple",
    "speaker": "en_female_dacey_uranus_bigtts",
    "audio_params": { "format": "mp3", "sample_rate": 24000,
                      "speech_rate": 0, "loudness_rate": -50, "bit_rate": 64000 },
    "additions": "{\"post_process\":{\"pitch\":0},\"disable_markdown_filter\":true}"
  }
}

响应：SSE 的 data: 行，每行 {"code":0,"data":"<base64>"}
  把每行 data 字段 base64 解码后**按行顺序**拼接，得到完整 mp3。
  code 为 0 / 20000000 表示成功 —— 但见下面那条 ⚠️。
```

**逐字事实**（`native/src/audio/dsh_doubao.c` 的 `dsh_doubao_request_body` /
`dsh_doubao_parse`，以及 `native/src/engine/dsh_speech_online_api.c` 的 `write_headers`）：

- `additions` 是一个**JSON 序列化字符串**（不是对象），服务端就是这么收的；
  它里面的键与 `post_process` / `disable_markdown_filter` / `explicit_language` 同级。
- **`additions` 里刻意不写 `explicit_language`** —— 那是刻意的，不是漏了
  （`native/tests/test_doubao.c` 有一条断言专门钉"请求体里**不该有** `explicit_language`"）。
- `sample_rate` 属于 **`audio_params`**，不是 `req_params` 顶层。
  （放顶层也能出声，服务端容忍，但那不是文档写法。）
- **计费字数要点亮才给**：加 `X-Control-Require-Usage-Tokens-Return: *` 之后，
  响应里才有 `usage.text_words`（"本次请求计费的文本字数（含标点）"）；少一个字符不是错，只是读不到。
- 本项目用**带 `/sse` 的那个端点**（实测 200 + mp3；不带 `/sse` 的不是流式音频，没试、不没事找事）。
- **`code 0` 不等于成功**：解出来的音频是**空**的必须单独判成失败，而且那句话要点出原因
  （§9.2 有实测形态）。`dsh_doubao.h` 顶上把这一条列成"三条实测得来的硬约定"之一。

关键参数范围（**字段与语义以官方文档为准**）：

- 官方文档：<https://docs.volcengine.com/docs/DoubaoVoice/HTTPChunkedSSEUnidirectionalStreaming-V3?lang=zh>
  —— 请求体 / 返回体的**完整字段表**见上面那条官方文档，本文不摘抄。
- `speech_rate ∈ [-50, 100]`（100 = 2 倍速，-50 = 0.5 倍速）。越界**如实拒**，不悄悄夹。
- `loudness_rate ∈ [-50, 100]`（100 = 2.0 倍音量、-50 = 0.5 倍，换算成 dB 只有 ±6.02）；
  本项目**总是发这个字段**（0 也发）—— 少一个字段与服务端"默认 0"虽然等价，
  但少一个字段就少一条可核对的证据。
- `pitch ∈ [-12, 12]`（在 `additions` 的 `post_process.pitch`，本项目固定 0、暂不暴露）。
- `format`：`mp3` / `pcm` / `ogg_opus` / `wav`；整文件用 **mp3**。
- `sample_rate`：`8000..48000`，默认 24000。
- `explicit_language`（在 `additions` 那个 JSON 串里）：**语义是「只念这个语种」，不是「提示语种」。**
  官方原文：

  > 显式指定朗读语种。开启后，**仅朗读指定语种的文本，其他语种的内容会被跳过或合成失败**。
  > `zh-cn`：中文为主，**支持中英混读**；`en`：**仅朗读英语**。
  > 注意：启用该参数后，输入文本须包含指定语种的内容，否则请求将无法正常返回。

  **不传该参数 = 正常中英混读**（2.0 音色的默认行为，官方字段说明写的是
  "Empty means normal Chinese-English mixed reading"）。取值（**以官方文档为准**，本文不再抄表）：
  `zh-cn` / `en` / `ja` / `ko` / `fr` / `de` / `es-mx` / `it` / `pt` / `pt-br` / `ru` / `th` / `vi` /
  `id` / `ms` / `ar` / `pl` / `tr` / `sv` / `fil`（菲律宾语）。

  ⚠️ 官方表里**没有 `es`**（只有 `es-mx` 墨西哥西语）、**没有 `hi/ta/bn/el/he/uk/fa/ur`**，
  另有本方案早期那张表漏掉的 `pt-br` 与 `fil`。传表外的值等于让请求失败，
  **宁可什么都不传** —— 而本项目的做法正是"什么都不传"。
- `additions.enable_language_detector`：自动语种检测（默认 `false`）。
  ⚠️ **官方字段表里没有这一项**（那张表只有 max_length_to_filter_parenthesis / silence_duration /
  disable_markdown_filter / disable_emoji_filter / latex_parser / explicit_language /
  explicit_dialect / aigc_watermark / aigc_metadata / post_process）。
  实测传了不报错、能出声（§9.2 的 E），但**未文档化 = 随时可能变**，所以不用它。
- `speaker`：控制台「音色库」 / 官方音色列表里的音色 ID。
- `additions.context_texts`（**array**）：**语音指令**（配置朗读语气）—— 在 `additions` 那个
  JSON 串里、**不是 `req_params` 顶层**，**仅 2.0 音色支持**，**字段文字不参与计费**。
  怎么用、以及"传错了它也不报错"这些坑见 **§9.6**。

### 2.3 ⚠️ Resource ID 必须与音色配套

填错会返回 `40000001 参数错误`。这条是新手最容易踩的：

| 音色 ID 特征 | 必须配的 Resource ID |
| --- | --- |
| `*_uranus_bigtts`（2.0 音色） | `seed-tts-2.0` |
| `*_mars_bigtts` / `*_moon_bigtts`（1.0 音色） | `seed-tts-1.0` |
| `S_` 开头（声音复刻） | `seed-icl-1.0` / `seed-icl-2.0` |

**决定**：本项目**只用 2.0 音色**（`seed-tts-2.0`），**不做声音复刻**。
好处是 Resource ID 恒定，设置里做成**只读**、不给用户改的机会。

**内核里那条判断只有一句**（`native/src/audio/dsh_doubao.c` 的 `dsh_doubao_resource_for`）：
`_mars_bigtts` / `_moon_bigtts` 结尾的走 1.0，**其余一律走 2.0**（别自己加规则）。
`S_` 那一档**内核不认**（本项目不做复刻）—— 只有诊断脚本
`tools/probe-doubao.mjs` 里还留着 `^S_ → seed-icl-1.0` 那一格，那是脚本自己的实验开关
（`--resource-id` 覆盖）。

⚠️ 还有一条现状值得写下来：设置里 `doubaoResourceId` 这一格**今天表示不出"没填"** ——
读设置时就把默认值 `seed-tts-2.0` 落进去了，所以"按音色后缀推"那一支在实际发音这条路上
**走不到**。这是刻意的现状，不是漏移植。

### 2.4 错误码（做成人话提示，别把原始码丢给用户）

`native/src/audio/dsh_doubao.c` 的 `dsh_doubao_error_sentence` 是唯一那张表
（**与翻译那张不是同一张**）：

| 码 | 含义 | 给用户的提示 |
| --- | --- | --- |
| `0` / `20000000` | 成功（**但还要看有没有音频**，见 §9.2） | — |
| `40000001` | 参数错误 | 「音色 ID 与模型版本不配套（或者文本、语速这些参数不对）—— 去「语音」那一页核对音色。」 |
| `40300001` | 鉴权失败 | 「API Key 不对，或者语音服务没开通 / 实名认证没做完。」 |
| `40402003` | 文本超长 | 「这段文本太长，语音服务退回来了（正常不该出现，我们是按段发的）。」 |
| `45000000` | 客户端错误 | 「语音服务说这次请求有问题（参数或文本）。」 |
| `55000000` | 服务端错误 | 「火山引擎服务端出错，稍后再试一次。」 |
| quota 类 | 试用额度用尽 | 「试用额度已用完，需在控制台开通正式版」 |
| `45000030` / `requested resource not granted` | 账号下没开通这个音色 / 服务 | 「去控制台开通服务，并在音色管理里开启要用的**试用音色**」 |

⚠️ 两条必须记住的：

1. **这张表是"精确匹配"的**：`45000000`、`55000000` 这几个是**整码**，不是前缀。
   所以 `45000030` 落进的是**兜底那一档** —— 原文「服务端原话 + `code`」一起给
   （诊断脚本里对 `45000030` 有专门一格人话，内核那张表里没有；这一档靠服务端原话
   "requested resource not granted" 才认得出来）。
2. **不许把"没开通 / Key 错"说成"参数错误"** —— 那会把用户指去改错的地方
   （`native/tests/test_doubao.c` 里有一条断言专门钉"鉴权错**不许**说成音色参数问题"）。

### 2.5 计费

**按字符计费**；新用户有**免费额度**，会耗尽。所以：

- **测试时不要连环跑** —— 这也是诊断脚本（probe）优先、完整测试克制那条纪律的具体应用；
- 界面上保留「检测凭据」让用户随时现测，但每次只发**一个短样本词**
  （内核自带的样本词表：英文 `apple`、中文 `苹果` …）；
- 「检测凭据」**刻意绕开缓存**真发一次请求 —— 走缓存的话，Key 被撤销了照样报 ✓；
- 输出侧还有一条更省钱的：**缓存先查、再决定发不发请求**（§6.4）。

## 三、为什么不能塞进现有「在线模板」

从前的「在线发音」在参考实现的 `OnlineSpeech.cs`（**已删除**，见 §四 / §九），
是 **GET 一个 URL 模板**（有道 `dictvoice`、Google `translate_tts`），
`Fetch()` 只做 `GET + UA 伪装 + 按魔数嗅探 MIME`。

豆包是 **POST + 三个自定义 header + JSON body + SSE 流式解析**，无法表达为一个 URL 模板。
所以豆包要作为**独立 provider** 实现，并**替换**掉 URL 模板那条「在线」实现，
而不是往 `onlineTemplates` 里塞一行。

好消息：这条路的**依赖成本是零** ——

- **发**这件事由壳里已有的那条 HTTP 通道完成（`shell/Lookup.Host/TranslateHttp.cs`，
  语音与机器翻译共用同一条），**不引入任何新 DLL**；
- **解析**（SSE 的 `data:` 行、base64 拼接、错误码翻人话）全在**零依赖的内核**里
  （`native/src/audio/dsh_doubao.c`），**不引任何 JSON 库**：内核自带
  `json_reader` / `json_writer` / `dsh_base64`。

这条"内核—平台—内核"三段式与机器翻译那条路是同一个形状（见 `shell/Lookup.Host/ShellBridge.cs`
里 `translate:text` 那一段的说明）。

## 五、实现方案（分 5 个阶段，按本仓库的落点写）

> **前置**：§〇 的凭据（自己的）到手、且 `tools/probe-doubao.mjs` 验通之后，
> 再开始写这里的代码。

### 阶段 1 —— 新增豆包 provider（内核那一半）

- **纯逻辑**住 `native/src/audio/dsh_doubao.c` + `.h`：
  - `dsh_doubao_request_body(text, speaker, speech_rate, loudness_rate)` → 请求体 JSON；
  - `dsh_doubao_resource_for(speaker)` → 模型版本（**必须与音色配套**）；
  - `dsh_doubao_speaker_for(mixed, language, en, zh)` → 这次该用哪个嗓子（§6.1）；
  - `dsh_doubao_parse(status, body, len, out)` → **SSE 回包 → 音频字节**：
    逐行取 `data:` 行、JSON 取 `code` 与 `data`、base64 解码后**按行顺序拼接**；
    `code != 0/20000000` 记错误（但**继续看后面的行** —— 服务端有时在错误码之后还会补一行说明）；
  - `dsh_doubao_error_sentence(code)` → 人话（§2.4），**不把原始码丢给用户**。
- **接口那一半**住 `native/src/engine/dsh_speech_online_api.c`：
  `dsh_speech_online_plan`（说该发什么）/ `dsh_speech_online_test_plan`（检测凭据要发哪几次）
  / `dsh_speech_online_accept`（回包是什么意思）。接口定义与逐条约定在 `abi/lookup.abi.json`。
- **壳只搬运**：`shell/Lookup.Host/Speech.cs` 把 plan 给的 `url` / `headers` / `body`
  原样发出去（`TranslateHttp.Post`），把 **HTTP 状态 + 整段回包 + 耗时**交回 `accept`。
  ⚠️ 回包是 SSE，壳要**整段缓冲**再交进来，**不许自己边收边解析**。
- 体积上限 / 超时 / TLS 这套规矩**照抄参考实现那一套的语义**（现在在 `TranslateHttp.cs`），
  语义**与 `tools/probe-doubao.mjs` 一致**（两处实现、同一份字段说明）：
  诊断脚本先验通，再照它写实现。
- **错误码按 §2.4 的表翻成人话。**

### 阶段 2 —— 设置扩展

- `native/src/engine/dsh_settings.h` 的 `dsh_speech_settings` 里这几格：
  - `doubaoApiKey`（与 `volcengine.apiKey` **镜像**，§〇 ①）；
  - `doubaoResourceId`（默认 `seed-tts-2.0`，界面上只读）；
  - `doubaoSpeakerEn`（英文音色 ID）、`doubaoSpeakerZh`（中文音色 ID）；
  - `doubaoFormat`（默认 `mp3`）；
  - `doubaoLoudnessEn` / `doubaoLoudnessZh`（两个音色各自的响度补偿，§9.5）。
- 规范化（`native/src/engine/dsh_settings.c`，约定照参考实现的 `NormalizeSpeech`）：
  `rate` 夹到 -10..10；`accent` 只认 `uk` / `us`、其余一律 `auto`；
  `doubaoApiKey` trim 之后空的当没填；`doubaoResourceId` / `doubaoFormat` 兜默认值；
  两个 speaker 允许为空、**Trim**；响度夹到 -50..100（**没设过就保持没设过** ——
  "没设过"与"设成 0"不是一回事，前者用内置表）。
- ⚠️ **NULL 与空串不是一回事**（`dsh_settings.h` 里点过这一条）：
  `NULL` = 字段从来没设过 → 用内置默认音色；**空串 = 用户的明确选择，留着**
  （清空输入框保存后再打开，不该被默认值顶回来）。
- `speech` / `volcengine` / `translate` 三节里**没建模的子键一律原样搬运、绝不丢**
  （`keep_extra` / `foreign_pair`）—— 老配置里残留的 `translate.dictionaryFirst` 会被原样带过去，
  **不是错误**。

### 阶段 3 —— 三层音源接线

- 在线那一层的 `label` 是「豆包语音（在线）」；**能不能走只看填没填 Key**（§〇 ⑥），
  不可用时 `available=false` + 那一句人话（界面原样显示）。
- **音色按 §6.1 选**（与"混不混排"配套，不能各选各的）。

  | 文本 | 音色 |
  | --- | --- |
  | 中英混排 | **中文音色**（硬约定：英文音色念混排回 0 字节且不报错） |
  | 纯中文 | 中文音色 |
  | 纯英文 / 其它语种 / 判不出 | 英文音色（中文音色没配时反过来顶上；两个都没配 → 如实报"没配音色"） |

  > ⚠️ **请求体里的 `explicit_language` 一律不传** —— 所以这张表**只有音色一列**。
  > 早期方案里"纯英文传 `en`、纯中文传 `zh-cn`"那一套已经**不采用**（§6.1.1 留作记录）。

- 对应的音色为空 → 该条 `online` 不可用，落到 `system`（如实说明，不报错地换层）。
- 语种策略：内核那套统一判定（字形 + 词典标题两条线索，`dsh_language_decide`）
  加上 **`dsh_language_is_mixed`** —— **"混不混"必须单独问出来**，否则调用方判不了。
- **优先级顺序就是 `dict → online(豆包) → system`**：`auto` 与显式 `dict` 的 order 都是
  `[dict, online, system]`；显式 `system` → `[system, online]`；显式 `online` → `[online, system]`。
  （"这一次的覆盖"那套规则见 `dsh_speech_plan` 的 `overrides_json`：
  **键在 = 强制这个值**，那一层不可用就如实报**它自己的**原因，**绝不不报错地回落到别的层**；
  **键不在 = 全套照设置**。）
- 语速映射：设置里 `rate(-10..10)` → `speech_rate = clamp(rate * 5, -50, 100)`；
  `pitch` 暂不暴露、固定 0。

### 阶段 4 —— IPC

- `speech:setSettings` 透传 `doubaoApiKey / doubaoResourceId / doubaoSpeakerEn / doubaoSpeakerZh /
  doubaoFormat / doubaoLoudnessEn / doubaoLoudnessZh`，**不再读写 `onlineTemplates`**。
- `speech:testDoubao`：拿样本词真发一次豆包，报状态码 / 字节 / 耗时 / 计费字数 / **人话错误**。
  ⚠️ 三项与"真念一段话"不同：① 走的是 `test_plan`（音色由**界面正在填的那个**定，
  不是设置里存着的）；② 拿到的音频**不播也不留**（但**必须还掉** —— 内核分配的内存只有
  `dsh_release` 能还）；③ 每一项都要报回结果，所以"两项里有一项没配音色"也要如实说，不许整条抛。
- `speech:status / speech:speak` 的**形状不变**，只是「online」背后换成了豆包
  （回包里 `voiceId` 是音色 id、`voiceName` 是**界面上的说法**，名字问内核要
  `dsh_speech_speaker_label`，**壳里不许再抄一张表**）。

### 阶段 5 —— 前端

- `web/shared/types.ts`：
  - `SpeechSettings` 带上 `doubaoApiKey / doubaoResourceId / doubaoSpeakerEn / doubaoSpeakerZh /
    doubaoFormat / doubaoLoudnessEn / doubaoLoudnessZh`；**没有 `onlineTemplates`**；
  - 音源只有三档 `dict` / `system` / `online`（`SpeechOption.source`），`online` 即豆包；
  - `DoubaoView` 里**没有完整的 Key，只有掩码**（`hasApiKey` + `apiKeyMasked`）。
- `web/src/floating/main.ts`：音源文案里的「在线发音」→「豆包语音（在线）」，相关 toast 同步。
- `web/manager.html` + `web/src/manager/main.ts`：「语音」页那一组豆包配置：
  - 隐私提示（「发音时要念的词会发给该服务」）+ 说明这一路是第三方服务；
  - **API Key（`type="password"`，平时只显示掩码）**、TTS 模型（**只读**，`seed-tts-2.0`）、
    英文音色、中文音色、两个音量的滑块；
  - 「保存」+「平衡音量」+ 清缓存 + 缓存说明；
  - **API Key 旁边要有一行小字**：怎么申请（§2.1 那四步 + 链接）。
- 「翻译」页那张「检测凭据」：**一个按钮两行字**（语音合成 + 机器翻译）——
  两件事是同一把 Key、同一个平台，分两个按钮等于让用户点两次再自己拼结论。

## 六、关键实现细节

### 6.1 语种策略：**混排是常态 —— 先判「混不混」，再决定用谁念**

词典正文天然中英混排（`apple 苹果，一种水果。An apple a day…`），
而 `explicit_language` 是**限制**不是提示。
**按"检测到的主语种"直接传参，会让中文被跳过甚至整条失败。**
所以本项目的做法比"按语种传参"更彻底：**这个参数一个字都不传**。

```
① 判文本是不是中英混排（忽略标点/数字后：汉字 > 0 且拉丁字母 > 0）—— dsh_language_is_mixed()
     ├─ 是混排 → 音色用中文音色（硬约定：英文音色念混排服务端不报错地回空句子）
     └─ 不是混排
          ├─ 中文 → 音色用中文音色
          └─ 其余（含纯英文、以及表外语种）→ 音色用英文音色
② 音色为空时的回落（`dsh_doubao_speaker_for`）：
     · 该用中文音色而中文音色没配 → **回落到英文音色**（用户只配一个也能出声，功能不缺）；
     · 该用英文音色而英文音色没配 → 用中文音色顶上；
     · 两个都没配 → 如实报「没配音色」，在线那一层不可用，落到系统语音。
③ **请求体里一律不写 `explicit_language`** —— 所以"传什么值"这个问题在本项目里不存在。
```

**为什么混排时用「不传 + 中文音色」**：

- 不传 = 官方默认的 *normal Chinese-English mixed reading*；
- 英文音色（`en_*`）**念混排实测是 0 字节的空句子，而且不报错**（§9.2 的 A/B 两组）
  —— 所以这条**不是"哪个好听"的偏好，是"不照做就出不了声"**；
- `zh_*` 2.0 音色的默认行为就是中英混读；其中
  `zh_female_yingyujiaoxue_uranus_bigtts`（Tina老师 2.0）官方描述是「中文/英式英语」，
  是混排场景最稳的候选。

**实现提示**：语种判定只返回**一个主语种**，但它内部已经按字形数过了 ——
**得把"是否混排"单独暴露出来**（`dsh_language_is_mixed`），否则调用方判不了。
参考实现的 `LanguageDetector.Detect()` 当年也是这个毛病，解法一样。

#### 6.1.1 原方案的纯语种映射表（**已不采用**，留作记录）

早期方案是"按检测出的语种传 `explicit_language`"，表长这样：

| 检测结果 | 原方案的 `explicit_language` |
| --- | --- |
| en | en |
| zh | zh-cn |
| ja | ja |
| ko | ko |
| fr / de / it / ru / th / vi / id / ms / ar / pl / tr / sv | 同名小写 |
| es | es-mx（官方表里没有 `es`） |
| pt | pt（另有 `pt-br`，巴西葡语；要区分时用 `pt-br`） |
| fil（菲律宾语） | fil |
| 其余（hi / ta / bn / el / he / uk / fa / ur…） | 空（交给豆包自动判定） |

**为什么不采用**（这段推理仍然有效，所以留在这里）：

- 这张表的检查标准是"官方取值列表里有没有这个值"，而**表外的值一律不传** ——
  传错语种等于"只念这个语种"，而这段文本里没有它 → 请求无法正常返回；
- 更根本的一条：**这个参数是限制不是提示**。词典正文里中英混排是常态，
  一旦按"主语种"传参，另一语种就被跳过 —— 那正是 §9.2 里"点朗读只出声念了英文"那类最难查的 bug；
- 所以现在的做法是**整条不传**（`dsh_doubao_request_body` 里那句注释点了名：
  "这里刻意不写 `explicit_language`"），语种只用来**挑音色**。

#### 6.1.2 可选进阶：按语种切段、分别合成再拼接（**不建议进第一版**）

质量最好（英文词用英文音色、中文用中文音色），但代价明确：

- **多次请求** —— 按字符计费，混排长文本会更贵；
- 要按脚本切分文本，并**拼接多段 mp3**（段间可能有轻微停顿）；
- 要与现有"300 字分段 + 预取"的朗读管线合并考虑，复杂度上一个台阶。

先用 §6.1 的「混排 → 不传 + 中英混读音色」跑通；听过效果之后再决定要不要做这个。

### 6.2 语速映射

`rate ∈ [-10, 10]` → `speech_rate = clamp(rate * 5, -50, 100)`：0 保持 0，两端到 ±50，
够用且不夸张。⚠️ **必须换算**：直接把 -10..10 递过去，服务端当"几乎没变速"，
用户拖到两端会听不出差别。

### 6.3 隐私与密钥存放

- 豆包要有明确的「发音时要念的词会发给该服务」提示（页面上那行就是它）。
- **API Key 明文写进 `%APPDATA%\LookupApp\settings.json`**（与其余设置同库同明文）。
  个人桌面程序可接受，但**要在界面上写明这一点**，并提醒别把这个文件外发。
- 界面上 API Key 用 `type="password"` 输入框（挡住肩窥即可，不是加密），
  平时只把**掩码**当占位符（§〇 ①）。
- ⚠️ **没有"在线语音总开关"**（§〇 ⑥）：在线那一层通不通只看 Key 填没填。
  要"关掉在线"就把 Key 清空 —— 别再加一个开关，那会让"我开着却没走在线"变成一个要查的问题。

### 6.4 缓存

豆包输出的 mp3 直接进壳里那块音频暂存（`shell/Lookup.Host/Speech.cs`）：

- **缓存键是内容寻址的**：算在**请求体**上（`HashKey("online-v1|" + body)`）——
  请求体就是"这次要什么"的完整描述（音色 / 语速 / 响度 / 文本都在里面）；
- **键里不带 API Key** —— 换 Key（换账号）不影响已缓存音频，也避免 Key 出现在任何文件名里；
- **先查缓存、再决定发不发请求**：TTS **按字符计费**，而"同一个词反复点发音"是最常见的用法；
  少了这一步，每点一次就是一次真实请求（花钱、也慢几百毫秒）。
- 现状：**内存字典、上界 64 条、先进先出**（`MaxEntries`），**不落盘**
  （参考实现那一代还落盘）。要清就点界面上的清缓存（`speech:clearCache`）。

### 6.5 检测按钮用哪个样本词

用**内核自带的样本词表**（`dsh_doubao_sample_word`）：英文 `apple`、中文 `苹果`、
日文 `りんご` …（32 个语种，表外回 `"hello"`）。**分语种各测一次**
（英文音色 + 中文音色）：两个音色的 Key / Resource 配套关系是一样的，
但音色 ID 写错只有真发一次才发现。

⚠️ 这张表是**产品数据**，所以它住在内核里（界面与外壳一个字都不拼），用户改不了它。

## 七、风险与注意

- **第三方接口随时会变**：音色会增减、接口会改版、计费会调。
  所以界面上**必须保留「检测凭据」**随时现测，别把"能不能用"写死。
- **免费额度会耗尽**（quota 类错误）→ 提示用户去控制台开通正式版，
  不要表现为"莫名其妙没声音"。
- **联网延迟**：豆包每次发音都是网络请求（数百毫秒量级）。单词发音有原录音时不走它；
  无原录音 / 选中朗读才走，长文本仍按 300 字分段 + 预取，听感连贯。
- **离线场景**：断网时豆包失败 → 自动退回系统语音，已在优先级里处理。
- **中文音色留空**时，"汉语词条"会落到系统语音（离线）。这是**设计允许**的退回，不是 bug；
  但界面提示要说清楚，否则用户会以为豆包坏了。
- **`code 0` 不等于成功**（§9.2）：任何"请求成功"都不能当成"念出来了"的证据。
- **同一请求的合成结果有随机性**（§9.6 的坑 2）：拿"字节数 / 时长变了"当证据之前，
  先量一次抖动幅度。

## 八、附录：`tools/probe-doubao.mjs` 规格

**独立、可单独运行、默认只发一次请求、不依赖程序的任何一版实现。**

```
用法：
  node tools/probe-doubao.mjs --api-key <key> [--speaker <音色ID>] [--text <文本>] [--out <文件>]
  node tools/probe-doubao.mjs --api-key <key> --mixed-test    # 中英混排专门测试（发 5 次），见 §8.1
  node tools/probe-doubao.mjs --api-key <key> --tone-matrix   # 语音指令（context_texts）实测矩阵
  node tools/probe-doubao.mjs --list-voices                   # 打印候选音色表（离线，不发请求）
  node tools/probe-doubao.mjs --measure <目录>                # 只读已有的 mp3，量时长与语音电平（不发请求）

默认：
  --speaker  en_female_dacey_uranus_bigtts
  --text     apple
  --out      logs/doubao-probe.mp3

必须打印（缺一不可）：
  · 请求用的 speaker + resource-id（由 speaker 后缀推断，见 §2.3）+ 实际传的 explicit_language
  · HTTP 状态码、耗时 ms、音频字节数、嗅探出的 MIME、计费字数
  · 失败时：豆包错误码 + §2.4 的人话解释 + 响应片段（便于判断"回的是错误页还是音频"）
  · 音频落盘路径（供当场试听）
```

还有两个开关值得记住它的**理由**：

- **`--dump`**：把 SSE 的**每一条原始行**打出来。流式响应里"没有 data 字段"可能有多种成因
  （服务端只发事件号、发了纯文本的 OK、或者字段名与文档不一致），
  只看"0 字节 + 失败"分不清是哪种；没有它，A/B 那两组"0 字节"无法与"字段名不对"区分开。
- **`--show-body`**：打印请求体（确认字段落在 `additions` 里、而不是 `req_params` 顶层）。

**Key 从命令行或环境变量 `DSH_DOUBAO_API_KEY` 取，不许写进任何文件**
（回显也只给头尾：`a30dba13…47fc` 那种形状）。

### 8.1 `--mixed-test`：把「中英混排到底能不能全念」变成一次实验

这是这个诊断脚本**最重要的用途**。样本固定用一句真实混排：

> `apple 苹果，一种水果。An apple a day keeps the doctor away.`

它把 §6.1 的假设逐条验掉，**每组各存一个 mp3**，让人直接听：

| # | 音色 | `explicit_language` | 预期（待验证） |
| --- | --- | --- | --- |
| A | 英文音色 | **不传** | 中文可能被跳过 → 英文音色能不能读混排？ |
| B | 英文音色 | `en` | **中文会被跳过**（官方明确）—— 对照组，用来确认"限制"语义 |
| C | 中文音色 | **不传** | 应全部念出（§6.1 的首选方案） |
| D | 中文音色 | `zh-cn` | 应全部念出（官方说 `zh-cn` 支持中英混读） |
| E | 中文音色 | 不传 + `enable_language_detector=true` | 自动语种检测有没有帮助 |

输出必须给出**逐组的结论表**（每组：字节数 / 耗时 / 是否报错），并明确打印：

```
请试听 A~E 五个文件（logs/doubao-mixed-*.mp3），重点确认：
  ① 中文部分有没有被念出来（A/B 尤其要听）
  ② 英文单词发音是否自然（C/D 用的中文音色念英文好不好听）
听完再把 §6.6 的音色选择填回去。
```

**硬要求**：

- **默认只发一次请求**（计费按字符）。`--mixed-test` 是**唯一的多请求模式**：
  固定 5 次、样本极短，且运行前先说清楚"这会发 5 次请求"。
- API Key 从命令行或 `DSH_DOUBAO_API_KEY` 环境变量取，**不要写进任何文件**。
- 遇到 403 / quota 时给出可照做的下一步（见 §〇 ⑤ 的表）。
- **收尾不要直接 `process.exit()`**：实测在 fetch 用过的连接上直接退，
  Node 会在 Windows 上崩在 libuv 的 `async.c` 断言里（退出码 `0xC0000409`）——
  表现为"结论还没读到，先看到诊断脚本自己崩了"。改成只设 `process.exitCode`，
  让事件循环自己收干净。
- **分支必须互斥**（`if / else if` 链）：`process.exitCode` 不终止执行，
  写成平行 `if` 的话 `--mixed-test` 跑完还会接着跑一次单次测试 —— 白花一次计费请求，
  输出里也会凭空多出一段。

**为什么这个实验必须做、而不是靠推断**：`explicit_language` 的"限制"语义是官方写明的，
但"**英文音色在不传参数时能不能读中文**"官方没写。
这正是 §〇 坚持"先跑诊断脚本（probe）再写 provider"的原因 ——
没有它，这个不确定性会被埋进业务代码里，表现为"点朗读，只有英文出声"这种最难查的 bug。

**为什么这个前置件必须在写 provider 之前就有**：没有它，第一次真实请求会发生在
"业务代码写完、跑起来、点发音"那一刻 —— 失败时你分不清是 Key 错了、音色错了、还是 SSE 解析写错了。
有了它，这几件事被摊在几个独立步骤里逐个排除。

## 九、实测记录（`tools/probe-doubao.mjs` 跑出来的事实）

环境：本机调诊断脚本；音色按实测时指定的那两个 —— 英文
`en_female_authoritative-british_uranus_bigtts`（Charlotte）、
中文 `zh_female_vv_uranus_bigtts`（Vivi），Resource ID `seed-tts-2.0`。

> ⚠️ **程序里的内置默认音色是另一对**（英文 Dacey + 中文 Vivi，见 §6.6）。
> 下面凡出现 "Charlotte" 的地方，都是**当时那次实测用的音色**，
> 结论里"英文音色念 X 会怎样"这一类事实与该音色的具体 ID 无关，但**换音色要重测**。

### 9.1 连通性：通

`--text apple`（英文音色）→ HTTP 200、413~597ms、6,765 字节、嗅探 `audio/mpeg`、计费 5 字。

### 9.2 A~E 混排实验：结论与预期**不完全一样**

样本：`apple 苹果，一种水果。An apple a day keeps the doctor away.`（51 字，含标点）

| # | 音色 | `explicit_language` | 音频字节 | 实测时长 | 结论 |
| --- | --- | --- | --- | --- | --- |
| A | **英文音色** | 不传 | **0** | — | ✗ **整条不报错的失败** |
| B | **英文音色** | `en` | **0** | — | ✗ 同上 |
| C | 中文音色 | 不传 | 45,357 | 5.88s | ✓ |
| D | 中文音色 | `zh-cn` | 45,165 | 5.64s | ✓ |
| E | 中文音色 | 不传 + `enable_language_detector` | 47,085 | 5.88s | ✓（与 C 几乎没有差别） |

对照（用来判断"到底念没念英文"）：

| 对照 | 音色 | 文本 | 字节 | 实测时长 |
| --- | --- | --- | --- | --- |
| 1 | 中文音色 | `苹果，一种水果。` | 18,093 | 2.26s |
| 2 | 中文音色 | `apple. An apple a day keeps the doctor away.` | 32,301 | 4.03s |
| 3 | 英文音色 | 同对照 2 | 29,421 | 3.67s |

> 时长是拿**无头 Edge 的 `<audio>` / `decodeAudioData` 量出来的**（`tools/probe-doubao.mjs`
> 里那段测量；顺带证明这些 mp3 是能解码的），不是拿字节数估的。
> 今天要复量已有的样本可以直接跑 `node tools/probe-doubao.mjs --measure <目录>`
> —— 它只读文件、不发请求。

**① 英文音色念中英混排 = 0 字节，而且不报错。** 服务端只回：

```
event: 351
data: {"code":0,"message":"","data":null,"sentence":{"phonemes":[],"text":"","words":[]}}
event: 152
data: {"code":20000000,"message":"OK","data":null}
```

`code:0`、空句子、零音频 —— 而官方文档写的是「返回 0 则表示语音合成成功」。
**所以：判断成功绝不能只看 code，必须要求"真的拿到了音频字节"**，
否则在界面上就表现为"点朗读，什么都不响，也不报错"这种最难查的 bug。
（诊断脚本已经把这个形态**单独识别**并写明原因；内核里对应的那一档在
`native/src/audio/dsh_doubao.c` 的 `dsh_doubao_parse` 末尾，那句话也点了
"中英混排要用支持混读的中文音色"。）

**② 中文音色（Vivi）念英文会出声**：对照 2 有 32,301 字节 / 4.03s，
与英文音色的对照 3（29,421 字节 / 3.67s）同量级。
也就是说官方"Vivi 的多语种列表不含英语"**没有表现为跳过**，只是**好不好听要人耳判断**。
若别扭，换 `zh_female_yingyujiaoxue_uranus_bigtts`（Tina老师，官方描述「中文/英式英语」）。

**③ C ≈ 对照1 + 对照2（5.88s vs 2.26+4.03=6.29s）**，说明混排那句是中英都念了 ——
如果英文被跳过，C 应该只有 2.3s 上下；`explicit_language=zh-cn`（D）与不传（C）几乎一样长，
也符合官方"zh-cn 支持中英混读"。E（自动语种检测）和 C 一样长，**第一版不用它**。

**④ 由此确定第一版的规矩**（落到代码里的是 §6.1 那三条）：

| 文本 | 音色 |
| --- | --- |
| 中英混排 | **中文音色**（英文音色实测 0 字节，一票否决） |
| 纯中文 | 中文音色 |
| 纯英文 | 英文音色 |
| 其它 / 判不出 | **英文音色兜底**（见下面那条 ⚠️） |

并且——**请求体里一律不带 `explicit_language`**：上面 A/B 两组说明
"传 `en`"对混排是错的，D/C 两组说明"传 `zh-cn`"与"不传"没有差别，
那就干脆不传（少一个会传错的参数）。

> ⚠️ **一条没落进代码的实测结论**：这块早期写过一版"按音色的语种适用性修正"——
> 日语「こんにちは」中文音色 8,493 字节 ✓、英文音色 **0 字节** ✗，
> 于是结论是"非中英的语种要交给中文音色"。
> 但本仓库的 `dsh_doubao_speaker_for` 是「**混排或中文 → 中文音色；其余 → 英文音色**」，
> 所以**日语这类表外语种现在走的是英文音色**
> （`native/tests/test_doubao.c` 里有一条断言就写着"③ 日语（没配日语音色）→ 英文音色那一档"）。
> 也就是说：**那条实测结论没有落进内核**。写在这里是为了不让下一个人以为代码已经照实测改过了。

### 9.3 其它实测踩到的坑

- **Key 有 ≠ 服务开通**：一开始拿到的是 `code 45000030 requested resource not granted`
  （HTTP 200，不是 403）。这不是代码问题，只有去控制台把服务开通、并在音色管理里
  **开启要用的试用音色**才能解决。诊断信息要照 §2.4 的表翻成人话
  （内核那张表是精确匹配，`45000030` 走兜底那一档：服务端原话 + code 一起给）。
- **诊断脚本自己崩过一次**：在 fetch 用过的连接上直接 `process.exit()`，Node 会在 Windows 上
  崩在 libuv 的 `async.c` 断言（退出码 `0xC0000409`）—— 表现为"还没读到结论，先看到诊断脚本崩了"。
  改成只设 `process.exitCode`，让事件循环自己收干净（§八）。
- **分支必须互斥**：`process.exitCode` 不终止执行，所以 `--mixed-test` 跑完会接着跑单次测试
  （白花一次计费请求）。现在是一个 `if / else if` 链。
- **`--dump` 是必备开关**：没有它，A/B 的"0 字节"无法与"字段名不对"区分开。
- **试听要用系统浏览器打开**：侧栏那种沙箱 iframe **读不到 `file://` 下的相对资源**，
  打开本地的试听页会看到一排"总时长 0"的控件 —— 那是取不到文件，不是音频坏。
  用 Edge 打开同一个文件就正常。
- **`--instruction-shape` 这类"量错形状"的开关不能写死**：一旦在代码里写死 `array`，
  "传错形状"那两组实验其实仍按正确形状发出去了 —— 直到发现打印行里写着 `shape=array`
  才看出来。

### 9.4 音色分工

实测数据：

| 文本 | Charlotte（英） | Vivi（中英混杂） |
| --- | --- | --- |
| `serendipity`（单词） | 11,757 字节 ✓ | 14,829 字节 ✓（音色偏"中式"） |
| `apple 苹果，一种水果。An apple…`（混排句） | **0 字节** ✗ | 45,357 字节 / 5.88s ✓ |
| `こんにちは`（日语，`ja`） | **0 字节** ✗ | 8,493 字节 ✓ |

人耳试听后的判断（当时的原话）：

> Vivi 英文念得很好，**官网上她天生就是中英混杂音色**。她念单个单词时甚至还能模仿中式口音，
> 念句子时发音就很标准了 —— 不过这可能意味着她**不适合作为词条的语音音源**，
> 但是**可以作为文本朗读音源**。

**代码里落下来的两条规则与上面那段话不完全一样**（写清楚，免得对不上）：

1. **词条发音与选中朗读走的是同一条规划**（同一个 `dsh_speech_plan`），
   内核**不区分**"这是词头还是整段文本" —— 所以"单词归英文音色、整段归中文音色"
   那种按**用途**分工**没有**实现；实际的分工是按**文本**分的（混排/中文 → 中文音色，其余 → 英文音色）。
2. "Vivi 念单词偏中式口音"这条只体现在**人耳**上，代码里没有为它写任何分支。

### 9.5 音量调平：不同音色天生差 11 dB，用 `loudness_rate` 自动拉平

用户反馈：**"Charlotte 听起来音量偏低"**。这不是心理作用 —— 测出来差一个数量级：

方法（量电平的那段就住在 `tools/probe-doubao.mjs` 里，随时可复跑）：

1. **合成**：同一句参考文本（`An apple a day keeps the doctor away.`）让每个音色各念一遍 ——
   合成复用 `tools/probe-doubao.mjs`，**不抄第二份请求实现**；
2. **测量**：把 mp3 交给无头 Edge，用 Web Audio 的 `decodeAudioData` 解成 PCM 算电平 ——
   这样本仓库不必引入任何 mp3 解码依赖（程序里播放用的也是同一个解码器，量到的更贴近听感）；
   只读已有样本的那条路是 `node tools/probe-doubao.mjs --measure <目录>`（**不发请求**）；
3. **约定**：主用**有效语音电平**（按 20ms 分帧、剔除比整段 RMS 低 25 dB 的静音帧），
   同时报整段 RMS 与峰值 —— 整段 RMS 会把停顿算进去，念得慢的音色会被冤枉成"更轻"。

| 音色 | 时长 | 有效语音电平 | 整段 RMS | 峰值 |
| --- | --- | --- | --- | --- |
| Charlotte（英） | 2.42s | **−32.5 dBFS** | −33.4 | −14.2 |
| Vivi（中英混杂） | 3.05s | **−21.3 dBFS** | −22.7 | −8.0 |

**差 11.2 dB** —— 而官方 `loudness_rate` 只能表达 0.5x~2.0x（= ±6 dB），
所以只能"**抬轻的 + 压响的**"，让两条在一个中间值附近会合。

**闭环验证过**（不是"照公式算完就完事"）：把系数真的发出去重新合成、再量一遍 ——

| | 调平前 | 施加系数后 |
| --- | --- | --- |
| Charlotte | −32.5 dBFS | **−25.7 dBFS** |
| Vivi | −21.3 dBFS | **−25.8 dBFS** |
| 两者差距 | **11.2 dB** | **0.1 dB** |

**今天这条路的形态（与上面那次实验的区别，别照抄旧表）**：

- **内置表只有一个常量**：`DSH_DOUBAO_BUILTIN_LOUDNESS = -50`，而且
  **两个内置默认音色（Dacey / Vivi）都用它** —— 理由是"它们是候选里最响的两个，
  所以压到官方下限"（`native/src/audio/dsh_doubao.h`）。
  早期实验里那种"一个 +90、一个 −47"的**成对表已经没有了**。
- **表外的音色一律 0**（不补偿）—— 让用户用设置里那两个滑块去调。
- 设置里那两个滑块**优先**，但**只对它对应的那个音色生效**（比 id 时大小写不敏感）；
  "没设过"与"设成 0"不是一回事（`has_loudness_en` / `has_loudness_zh` 分开记）。
- **界面上有一条自动量的路**：「平衡音量」按钮（`web/src/manager/main.ts` 的
  `balanceDoubaoLoudness`）：先跑一次真实检测（不通过就不量），
  再用 `loudness: 0` 量**中性电平**，扫一个目标值，把算出来的 `loudness_rate` 写进设置。
  ⚠️ 用 `loudness: 0` 是为了量中性电平 —— 否则量到的值会随着用户拖那个滑块自己变，
  算出来的补偿会来回震荡。
- **代价（要记住的）**：把响的压下来，会让豆包整体比"什么都不调"轻一些，
  与词典原录音 / 系统语音之间的相对响度也跟着变了。
  要改成"只抬不压"就把那个音色的滑块设成 `0`（代价是两个豆包音色之间仍有差距）；
  若残余差距仍嫌大，唯一的路是**播放层增益**（Web Audio GainNode，不受 ±6 dB 限制）。

### 9.6 语音指令 `context_texts`：单词 / 短词组要"平常语气"

**要解决的问题**：豆包的合成会分析文本情感、朗读时带强烈语气 —— 念句子很好，
但**单个词条**的学习场景不需要它。用户的原话：
*"在处理单个词汇或者 2-3 个词组成的词组时用平常的语气读出。"*

**官方字段**：

- **`context_texts`（array，配置语音指令）**，位置在 **`additions` 那个 JSON 序列化字符串里**
  （与 `post_process` / `disable_markdown_filter` / `explicit_language` 同级），
  **不是 `req_params` 的顶层字段**；
- 官方示例：`"context_texts":["你可以用特别特别痛心的语气说话吗?"]`；
- **仅豆包语音合成模型 2.0 的音色支持**；
- **该字段的文字不参与计费**（计费只看要念的 `text`）。

**当时怎么用的**：参考实现的 `ToneInstruction.cs` 里那个 `PlainToneInstructionFor` 判断
"这段文本算不算单词 / 2-3 个词的词组"（检查标准：不含句末标点 + 词数 ≤ 3，
**中日韩两个字折算一个词** ⇒ 6 个汉字以内），是就带上
`请用平常、自然的语气朗读，不要加入夸张的情感。`；`BuildBody` 用
`additions["context_texts"] = new JArray(文案)` 塞进去（交给 JSON 库转义，不手拼 JSON）。

**⚠️ 本仓库的现状：产品那条路不转发这个字段。**
`native/src/audio/dsh_doubao.c` 的 `dsh_doubao_request_body` 拼出来的 `additions`
**只有** `{"post_process":{"pitch":0},"disable_markdown_filter":true}` ——
接口定义 `abi/lookup.abi.json` 里也**没有**任何"语气 / 指令"入参。
这个字段今天只在**诊断脚本**里被用到：
`node tools/probe-doubao.mjs --tone-matrix`（带 `--instruction` / `--instruction-shape` /
`--repeat-check`），那是给"要不要把这条规则做进产品"提供证据用的。

**它真的被采纳**（硬证据，不是"没报错"）：正对照指令「请用非常快的语速朗读这句话。」
把同一句 23 字的文本从 **5.04~5.88s** 压到 **3.89~4.44s**（两组各 3 次、**区间不重叠**）。
反过来，"平淡语气有没有更平淡"**没有**客观量能判（同一句话带 / 不带，时长区间完全重叠），
只能靠人耳 —— 所以没有为它写任何断言。

⚠️ **两条必记的坑**：

1. **传错了它不报错**：`context_texts` 传成**字符串**（不是数组）、或放到 **`req_params` 顶层**，
   服务端一律 **HTTP 200 / code 20000000 / 照常出音频** —— **没有任何警告**。
   只有正对照才能看出"没生效"，所以**别拿"请求成功"当证据**。
   （诊断脚本为此专门留了 `--instruction-shape string|toplevel|none` 这几档来**量错**。）
2. **同一请求的合成结果是随机的**：同参数连发 3 次，字节 **11757 / 8493 / 9837**、
   时长 **1.46 / 1.06 / 1.22s**、**三份 sha256 全不同**。
   所以**"字节数 / 时长变了"不能当"指令生效"的证据** —— 变化必须**大于抖动幅度**才算。
   先把抖动幅度量出来（`--repeat-check` 就是干这个的），再谈别的。

**非 2.0 音色这条路没验成**：本账号没有已开通的 1.0 音色 —— 拿 1.0 音色请求先回
`45000030 requested resource not granted`，**走不到"支不支持指令"那一步**；
程序对这种请求的反应是用**桩服务**模式（只对带 `context_texts` 的请求回 `40000001`）覆盖的。

**失败退回（参考实现的 `DoubaoSpeech.Fetch` 里做过）**：只有**参数类**错误码
（`40000001` / `4500xxxx`，但**排除** `45000030` 未开通、`403` 鉴权、`55000xxx` 服务端）
才**去掉指令重试一次**，重试成功后结果里透出「这次没用语音指令」；
`0 字节但没报错`的**这类失败不重试**（实测成因与指令无关）。
